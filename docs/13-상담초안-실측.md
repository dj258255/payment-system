# 13. 상담 답변 초안 — 실측 기록

*관련: [ADR-014](adr/ADR-014-cs-draft-port-and-number-guard.md), [ADR-012](adr/ADR-012-rule-based-cause-classifier.md), [11 AI 운영자동화 검토](11-AI-운영자동화-검토.md)*

---

## 왜 이 실험을 했나

ADR-014 에서 상담 초안 포트를 만들고 모델은 붙이지 않았다. 그때의 판단은
"모델을 붙일 가치가 있는지 모르니 잣대부터 만든다"였다.

그런데 잣대만 만들고 재지 않으면 잣대인지 알 수 없다. **실제 데이터를 흘려봐야 한다.**
그래서 앱을 띄우고 진짜 대사 불일치를 만들어 파이프라인 전체를 통과시켰다.

**구성한 것이 아니라 앱이 실제로 만들어낸 상태다** — 주문 생성 → 결제 승인 → (일부는) 부분취소
→ PG 정산 CSV 업로드 → 대사 실행 → 예외 큐 → 원인 제안 → 초안 생성 → 숫자 검증.

## 실험 0 — 진짜 데이터를 흘렸더니 검증기가 자기 초안을 반려했다

### 만든 시나리오 (실제 API 호출)

| 케이스 | 만든 방법 | 대사 결과 |
|---|---|---|
| 수수료 차감 | 승인 10,000원 → 정산 파일에 9,730원 | `AMOUNT_MISMATCH` |
| 부분취소 미반영 | 승인 후 3,000원 실제 취소 → 파일에 7,000원 | `AMOUNT_MISMATCH` |
| 설명 안 되는 차액 | 승인 10,000원 → 파일에 1,112원 | `AMOUNT_MISMATCH` |
| 내부에만 있음 | 승인만 하고 파일에서 제외 | `INTERNAL_ONLY` |
| 외부에만 있음 | 파일에만 있는 주문번호 | `EXTERNAL_ONLY` |

### 결과 — 4건 중 2건 오반려 (50%)

```
id=1  FEE_CALCULATION_DIFF  (DECISIVE)  verified=false
      rejected=['출처에 없는 금액: 270원', '출처에 없는 금액: 270원']
id=3  SUSPECTED_TAMPERING   (WEAK)      verified=false
      rejected=['출처에 없는 금액: 8,888원', '출처에 없는 금액: 270원']
id=4  PG_FILE_DELAY         (LIKELY)    verified=true
id=5  INTERNAL_RECORD_LOST  (LIKELY)    verified=true
```

**하필 최악의 두 건이 걸렸다.**

- `FEE_CALCULATION_DIFF` — **확신이 가장 높은 규칙**(DECISIVE). 차액이 수수료율과 원 단위까지 맞는 건
- `SUSPECTED_TAMPERING` — **초안이 가장 필요한 건**. 근거가 "설명되지 않는다"뿐이라 사람이 처음부터 조사해야 한다

### 원인 — 검증기의 계약이 잘못 정의돼 있었다

반려된 8,888 과 270 은 **분류기가 계산한 근거**다.

> `차액 8,888원이 수수료(270원)로도 취소로도 설명되지 않는다`

이 숫자들은 타임라인 항목의 금액이 아니라 `CauseClassifier` 가 산출한 값이다.
그런데 `FactPack.amounts()` 가 타임라인 금액만 모으고 있었다.

**검증기가 지키려던 것은 "타임라인에 있는 숫자만 써라"가 아니다.**
**"코드가 낸 숫자만 쓰고 모델이 지어낸 숫자는 쓰지 마라"** 가 맞다.
분류기는 코드이므로 그 근거의 숫자는 통과해야 한다.

### 왜 테스트가 못 잡았나

단위 테스트 7개가 전부 통과하고 있었다. **전부 손으로 만든 `FactPack` 을 썼기 때문이다.**
내가 만든 입력에는 내가 넣은 숫자만 있었고, 분류기가 계산한 값이 섞이는 상황이 없었다.

> 실제 데이터를 흘려야만 드러나는 결함이 있다. 이번 건이 그랬다.

### 고친 뒤

| | 고치기 전 | 고친 후 |
|---|---|---|
| 검증 통과 | **2 / 4 (50%)** | **4 / 4 (100%)** |
| 오반려 | `FEE_CALCULATION_DIFF`, `SUSPECTED_TAMPERING` | 없음 |

회귀 테스트 2건으로 고정했다 — 분류기 근거 금액이 통과하는 것과, 그럼에도
근거에 **없는** 숫자는 여전히 걸리는 것. 허용 범위를 넓힌 게 아니라 **제자리로 돌린 것**임을
두 번째 테스트가 지킨다.

### 실제로 나온 초안 (수수료 차감 건, 검증 통과)

```
[주문 01M195R3SMD6SEH13ECYSP9V37 확인 결과]

문의하신 주문 건의 처리 내역을 확인했습니다.

· 2026-08-30 · ORDER · 주문 생성 — 항목 1개
· 2026-08-30 · PAYMENT · 결제 IN_PROGRESS → DONE (USER, TOSS_PAYMENTS) — 승인 완료
· 2026-08-30 · LEDGER · 원장 분개 PAYMENT_APPROVED
· 2026-08-30 · RECONCILIATION · 대사 AMOUNT_MISMATCH — 내부 10,000 / 외부 9,730

확인된 금액: 100원, 270원, 10,000원

추정 원인(규칙 분류): FEE_CALCULATION_DIFF (DECISIVE)
  — 차액 270원 = 내부 10,000원 × 270 bps (기대 수수료 270원)
  ※ 제안일 뿐입니다. 확정은 담당자가 근거를 확인한 뒤 하십시오.
```

## 원인 커버리지 — 문서가 코드보다 한 칸 앞서 있었다

같은 흐름에서 하나 더 나왔다.

README 와 ADR-012 는 "8종 중 **6종**이 산수나 조회로 결정된다"고 적어뒀는데
**코드에는 규칙이 5개뿐**이었다. `TIMEZONE_BOUNDARY` 는 enum 에만 있고 아무도 내지 않았다.
ADR-012 표에서는 그걸 **자동 확정 후보**로까지 올려놨다.

**왜 못 잡았나**: 개별 규칙 테스트는 "이 입력에 이 원인이 나오는가"를 본다.
그래서 **아무도 안 내는 원인은 영원히 안 보인다.** 반대 방향으로 보는 테스트가 없었다.

`CauseCoverageHarnessTest` 가 그 방향을 본다.

| 등급 | 종수 | 원인 |
|---|---:|---|
| 산수로 결정 (DECISIVE) | 4 | 부분취소 미반영 · 수수료 차이 · **거래일 경계** · PG 파일 지연 |
| 정황으로 제안 (LIKELY) | 2 | 승인 직후 취소 · 내부 기록 유실 |
| 배제로 남음 (WEAK) | 1 | 위변조 의심 — **사람이 봐야 한다** |
| 규칙 없음 | 1 | `OTHER` — **AI 를 논할 자리** |

**세면서 배운 것**: 처음엔 "7종을 가른다"고 셌다. 위변조 의심까지 넣었기 때문이다.
그런데 그건 배제법으로 **남은** 것이지 결정된 게 아니다.
`결정 = DECISIVE + LIKELY = 6` 이 문서의 주장과 맞는 셈법이다.
이 구분이 흐려지면 **"규칙이 대부분을 해결한다"고 과장하게 된다.**

이제 테스트가 그 수를 고정한다. 규칙을 늘리거나 줄이면 깨지므로 문서와 코드가 같이 움직인다.

## 전후 정리

| 항목 | 전 | 후 | 근거 |
|---|---|---|---|
| 검증 통과율 (실데이터 4건) | 50% | **100%** | 실제 앱 구동, 위 재현 |
| 규칙이 결정하는 원인 | 5종 | **6종** | `CauseCoverageHarnessTest` |
| 문서·코드 일치 검사 | 없음 | **테스트로 고정** | 같은 하네스 |
| 지어낸 숫자 검출 | 100% (픽스처) | 100% (유지) | `DraftEvalHarnessTest` |
| 테스트 수 | 603 | **616** | 회귀 6 + 커버리지 3 + 어댑터 배관 6 |

**주의 — 여기 없는 숫자**: "상담 처리 시간 N% 단축" 같은 값은 없다.
상담원이 없으니 잴 수 없다. 있는 것은 **파이프라인이 실제로 통과하는가**와
**규칙이 어디까지 가르는가**뿐이고, 그 이상을 적으면 지어내는 것이다.

어댑터는 **모델 없이 배관까지 검증**했다(`OllamaDraftAdapterTest`, 6건). 스텁 HTTP 서버로
응답 파싱·프롬프트 내용·5xx·예상 밖 응답 모양·사실 없을 때 호출 안 함을 고정했고,
**모델이 지어낸 숫자가 어댑터를 통과해도 검증기에 걸리는지**를 끝까지 태워 확인했다.

만들어만 두면 검증되지 않은 코드가 남는다. 실제 모델을 붙이는 날 파싱이 틀려 있으면
그게 모델 문제인지 코드 문제인지 구분하느라 시간을 쓴다. 배관은 지금 고정할 수 있다.

### 섀도 모드가 푸는 문제

초안 품질을 재려면 "사람이 얼마나 고쳤나"를 알아야 하는데, 초안을 보여주면
사람이 그것에 끌려간다(앵커링). 그러면 **"고칠 게 없었다"와 "고칠 생각이 안 났다"가
구분되지 않는다.**

이건 이미 겪고 있는 문제다 — `ClassifierAccuracyMetrics` 가 자기 수치를 정확도가 아니라
**"일치율"** 이라고 부르는 이유가 그것이다.

섀도는 그 고리를 끊는다. 사람은 지금처럼 규칙 제안만 보고 확정하고, 초안은 옆에서
조용히 만들어져 기록된다. **정답 답변을 지어내지 않고도 대조가 가능해진다.**
홀드아웃(Stripe)과 selective-labels 대응(Feedzai)이 같은 발상이다.

모듈 순환을 피하려고 이벤트로 끊었다 — `assist` 가 `reconciliation` 을 의존하므로
반대로 부를 수 없다. 대사는 "확정됐다"고 알릴 뿐 누가 듣는지 모른다.
커밋 뒤에 처리되므로 초안 생성이 느리거나 실패해도 확정은 이미 끝나 있다.

### BYOK — 구독으로는 안 된다

"내 Claude 구독으로 돌릴 수 있나"를 확인했다. **안 된다.**

유료 Claude 구독(Pro/Max)은 Claude 앱과 **Claude Code 자체**를 커버하지만
**API 접근을 포함하지 않고 별도 과금**이다. 증거가 하나 더 있다 —
`ANTHROPIC_API_KEY` 가 환경변수에 있으면 **Claude Code 조차 구독을 무시하고 API 요금으로
청구**된다. 완전히 다른 경로다.

대신 "쓰는 사람이 자기 걸로 돌린다"는 발상 자체는 표준 패턴이 있다 — **BYOK**.
운영자가 자기 키를 설정에 넣고 요금은 그 사람 계정으로 나간다.
GitHub Copilot CLI·VS Code·Factory 가 같은 방식이고, Copilot CLI 는
**Ollama 같은 로컬 모델까지 같은 구멍으로** 받는다.

결제 도메인에서는 이게 편의가 아니라 **요건**이다 — "당신 키, 당신 계정, 당신 데이터".

키가 없으면 **기동 시점에 막는다.** 호출 시점에 실패하면 그때야 알게 되고,
그 사이 초안이 조용히 비어 나간다.

## 실험 2 — 실제 로컬 모델을 붙였다 (Ollama · Qwen3 8B)

### 왜 Ollama 인가, 왜 이 모델인가

**Ollama 는 운영에 쓰는 물건이 아니다.** 자체 호스팅 운영은 보통 **vLLM**(또는 SGLang, TGI)이다.

| | Ollama | vLLM |
|---|---|---|
| 용도 | 개발·테스트·엣지 | **운영 서빙** |
| 최대 처리량 | 41 tok/s | **793 tok/s** |
| P99 지연 | 673ms | **80ms** |

그런데 업계에서 널리 쓰는 구성이 정확히 이것이다 —
**"개발·테스트는 Ollama, 운영은 vLLM, 애플리케이션은 게이트웨이 뒤에서 그대로."**
`DraftPort` 가 그 게이트웨이다. 노트북 실험에는 Ollama 가 맞고, vLLM 으로 옮겨도 어댑터 하나만 갈린다.

**모델은 처음에 `qwen2.5:7b` 로 적었는데 근거 없이 고른 값이었다.**
찾아보니 지금 한국어 로컬 모델은 **Qwen3 8B** 가 1순위로 꼽혀 바꿨다.

### 먼저 걸린 것 — 추론 토큰과 프롬프트 레이블

**추론 토큰(thinking)** 이 켜져 있어 한 건에 19초가 걸렸다. Ollama 는 이걸 `thinking` 필드로
분리해 주므로 `content` 는 깨끗했지만, 시간이 두 배 넘게 든다. 서술만 시키는 일이라
껐다 — **19초 → 5초대**.

**프롬프트 레이블이 잘못돼 있었다.** `[쓸 수 있는 금액]` 이라고 썼더니 모델이 그걸 *잔액*으로
읽고 이렇게 썼다.

> 사용 가능한 금액은 10,000원과 270원입니다.

목록의 성격을 이름에 박아야 했다 — `[인용해도 되는 금액] — 사실이 아니라 <표기 허용 목록>입니다`.

### 실측 — 4건 × 3회 = 12회

| | 고치기 전 | 고친 후 |
|---|---|---|
| 검증 통과율 | **7 / 12 = 58%** | **12 / 12 = 100%** |
| 지연 중앙값 | 5,493ms | 5,233ms |
| 지연 최대 | 7,828ms | 6,997ms |
| 반려 사유 | `출처에 없는 날짜: 2026-09-06` (5건 전부) | 없음 |

**반려가 전부 같은 값이었다.** 에스크로 사실 문장의 `자동해제 예정 2026-09-06T...` 다.
코드가 만든 진짜 날짜인데, `FactPack.dates()` 가 `entry.at()`(사건이 일어난 시각)만 모으고
문장이 말하는 **다른 날짜**를 빠뜨렸다.

### 모델이 템플릿은 못 찾는 결함을 찾았다

이번 실험에서 나온 결함 3건은 **찾을 수 있는 층이 각각 달랐다.**

| # | 결함 | 발견 조건 |
|---|---|---|
| 1 | 분류기가 계산한 근거 금액이 반려됨 | 실데이터 + 템플릿 |
| 2 | 사실 문장 속 금액(`내부 10,000 / 외부 9,730`)이 반려됨 | **실제 모델**만 |
| 3 | 사실 문장 속 날짜(에스크로 해제 예정일)가 반려됨 | **실제 모델 + 반복 실행**만 |

2번은 템플릿이 절대 못 찾는다. 템플릿은 `amounts()` 를 그대로 찍을 뿐
**사실 문장을 읽고 인용하지 않기 때문**이다. 3번은 12회를 돌려야 보였다 —
모델이 매번 같은 문장을 쓰지 않으므로 1회 실행으로는 놓친다.

셋 다 뿌리가 같다 — **구조화 필드만 모으고 문장 속 값을 빠뜨린 것.**

### 정규식 하나가 더 있었다

날짜를 뽑을 때 `\b(\d{4}-\d{2}-\d{2})\b` 로 짰다가 테스트가 잡았다.
`2026-09-06T11:06` 의 `T` 는 **단어 문자**라 뒤쪽 `\b` 가 성립하지 않는다.
ISO 시각이 통째로 안 잡혔다. `(?!\d)` 로 바꿨고, 검증기 쪽 패턴도 같은 이유로 함께 고쳤다.

### 실제로 나온 모델 초안

**수수료 차이 (DECISIVE) — 쓸 만하다**

> 주문번호 01M196J2BAGHT2Z70GYJH4N9M5의 결제는 2026-08-30 승인 완료되었습니다.
> 대사 AMOUNT_MISMATCH로 인해 내부 10,000원과 외부 9,730원의 차액 270원이 발생했습니다. 확인 중입니다.

**위변조 의심 (WEAK) — 쓸 만하지 않다**

> 2026-08-30 결제 승인 완료 및 주문 상태 PAID 확인 중입니다.
> 에스크로 보류 자동 해제 예정일은 2026-09-06입니다.

### 남은 품질 문제 — 검증만으로는 안 잡힌다

**숫자는 다 맞는데 내용이 문제다.** 이건 `NumberGuard` 의 일이 아니다.

1. **내부 용어가 샌다** — `AMOUNT_MISMATCH`, `PAID` 같은 enum 이 고객용 문장에 그대로 나온다
2. **하필 어려운 건에서 약하다** — 위변조 의심 건은 초안이 가장 필요한 자리인데,
   모델이 정작 문제(설명되지 않는 8,888원 차액)를 말하지 않고 에스크로 일정만 읊었다

**2번이 중요하다.** 규칙이 못 가르는 자리에서 모델이 뭔가 해줄 것을 기대했는데,
**작은 로컬 모델로는 거기가 제일 약했다.** 업계 기대치와도 맞는다 — Uber Genie 도움률 48.9%,
Meta 인시던트 RCA 상위 5개 안 42%.

> **그래서 지금 결론**: 검증기는 제 몫을 한다(지어낸 숫자 100% 차단, 오반려 0%).
> 그런데 **초안 품질은 아직 상담원에게 내놓을 수준이 아니다.**
> 다음은 모델을 키우는 것(vLLM + 더 큰 모델)이 아니라 **프롬프트에서 내부 용어를 막고,
> 어려운 건에 어떤 컨텍스트가 더 필요한지**를 보는 것이다.

### 자동화가 얼마나 됐나 — 정직하게

| 항목 | 값 | 근거 |
|---|---|---|
| 초안 자동 생성 | **100%** (12/12) | 실측, 사람 개입 0 |
| 지어낸 숫자 차단 | **100%** | 픽스처 + 실측 |
| 오반려 | **0%** (전 50% → 58% → 0%) | 실측 3회차 |
| 초안 생성 지연 | 중앙값 **5.2초** | 실측 12회 |
| **바로 발송 가능한 초안** | **측정 안 함** | 상담원이 없다 |

마지막 줄이 핵심이다. **"상담 시간 N% 단축" 같은 숫자는 여기 없다.**
초안을 만들고 검증하는 것까지는 자동화됐지만, **그게 쓸 만한지는 사람이 판단해야** 하고
그 사람이 없다. 있는 것만 적는다.

## 아직 못 한 것

**초안이 쓸 만한지를 재지 않았다.** 검증 통과율은 100%지만 그건 "지어낸 숫자가 없다"는
뜻이지 "보낼 만하다"는 뜻이 아니다. 실제로 위변조 의심 건의 초안은 문제를 말하지 않았다.

이걸 재려면 **상담원이 초안을 얼마나 고치는가**(편집 거리)를 봐야 하고, 그 사람이 없다.
섀도 모드가 그 순간을 위해 준비돼 있다 — 사람이 확정할 때 초안이 조용히 기록되므로,
상담원이 붙는 날 앵커링 없는 표본이 쌓이기 시작한다.

**외부 모델(Anthropic)로는 재지 않았다.** 어댑터와 배관은 검증했지만, 생성형 AI 는 아직
금융권 망분리 예외가 아니라 결제 데이터를 내보내지 않았다.

**vLLM 으로 옮기지 않았다.** 지금 병목은 처리량이 아니라 초안 품질이다.
처리량이 문제가 되는 시점(동시 상담원 다수)이 오면 어댑터를 하나 더 만든다.
