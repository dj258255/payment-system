# 운영자용 타임라인 서술 — 사례조사와 설계 (2026-09-05)

> 작업 중 문서. 만들면서 채운다.

## 0. 왜 이걸 만드나

`docs/11` 이 처음부터 자리를 지목해 뒀는데 비어 있었다.

> **그럼 어디가 AI 자리인가**: 어드민 화면이 20개인데 "주문 X번에 무슨 일이 있었나"를
> 한 번에 보는 곳이 없다. **흩어진 사실을 시간순으로 엮는 서술** — 판단이 아니라 서술이다

> **분류는 규칙이 낫고, 서술은 AI가 낫다. 둘을 섞으면 안 된다.**

그런데 지금까지 붙인 모델 둘은 이랬다.

| | 무엇 | 결과 |
|---|---|---|
| 상담 초안(13 문서) | 서술 — 다만 **고객용** | 검증 통과율 58 → 100% |
| 잔여 원인(14·15 문서) | **분류** | **껐다** — 규칙 대비 얻는 것이 0 |

**분류 쪽을 껐으면 서술 쪽을 켜야 그 판단이 완성된다.** 운영자용 서술이 비어 있었다.

---

## 1. 사례조사 — 업계는 이 자리에 무엇을 하나

### 토스페이먼츠 — 로그 분석·해결책 자동 제시 (기술지원)

n8n(워크플로 자동화)과 LLM 엔진을 연결해 **로그를 읽고 문제 해결책을 자동으로 제시**한다.
목표는 **10분 이내 응답**. 판단이 아니라 <b>흩어진 로그를 읽고 뭐가 문제인지 말해주는</b> 자리다.
지금 만들려는 것과 성격이 같다.

### 카카오페이 — 결제 MCP · Agent Toolkit (2025.08)

AI 에이전트가 결제 API를 호출하게 하는 **개발자용** 툴킷. Tool 8개
(`demo_payment`·`ready_payment`·`approve_payment`·`get_payment`·`cancel_payment` +
정기결제 3종). 안전장치는 **화이트리스트 기반 도구 필터링과 액션 단위 권한**
(`payment: { get: true }`)이다.

**이건 이번에 안 한다.** 고객 결제 API를 에이전트에게 여는 것은 ADR-008(AI 에 쓰기 권한을
주지 않는다)과 정면으로 부딪힌다. 카카오페이가 화이트리스트와 액션 권한을 먼저 깐 이유도
같은 문제를 풀기 위해서다. 원칙을 흔들면서 붙일 자리가 아니다.

### 해외 — 분쟁/차지백 증거 조립

결제·주문·CS 시스템에서 증거를 모아 **대응 자료(representment) 패키지를 조립**하고
카드망 기한을 추적한다. 승소율 30~40% 개선을 주장한다.

**이것도 이번에 안 한다.** 더 크고, 분쟁 실데이터가 없어 검증이 안 된다.

### 그래서 고른 것

**운영자용 타임라인 서술 하나.** 재료가 이미 다 있고(11개 도메인 조회 API, 사실 계약,
숫자 출처 검증), 읽기 전용이라 ADR-008 을 안 건드린다.

## 2. 설계

```
OrderTimeline(11개 도메인)  ← 상황 13 에서 만든 조회
        ↓
    FactPack                ← 상황 15 에서 만든 계약. 숫자·날짜를 값으로 함께 낸다
        ↓
 TimelineNarrativePort      ← 템플릿이든 모델이든 여기서 갈린다
        ↓
 NumericProvenanceGuard     ← 서술의 모든 숫자가 FactPack 에 있는지 대조
        ↓
   운영자 화면 (읽기 전용)
```

### 고객용 초안과 무엇이 다른가

받는 사람이 운영자다. 그래서 **가드가 줄어든다.**

| | 고객용 초안 | 운영자용 서술 |
|---|---|---|
| 내부 용어 | **막아야 한다**(누출 0/12 를 쟀다) | **그대로 나와야 한다** — 화면과 대조해야 하니까 |
| 말투 | 다듬어야 한다 | 상관없다 |
| 없는 숫자 | 버린다 | **버린다** (유일하게 남는 위험) |
| 나가는 곳 | 고객 | 사내 화면 |

### 기본은 모델 없음

`TemplateNarrativeAdapter` 가 기본이다. 두 가지를 한다.

1. 모델이 없어도 화면이 비지 않는다
2. **모델이 넘어야 할 자(尺)가 된다** — 모델 서술이 이것보다 나은지 재지 않으면
   "붙였다"만 남는다. 잔여 후보에서 그걸로 한 번 데었다

일부러 잘 쓰지 않는다. 시간순으로 잇기만 한다. **이 문장이 이미 충분히 읽을 만하면
모델이 필요 없다는 뜻이고, 그것도 답이다.**

## 3. 만든 것

| | |
|---|---|
| `TimelineNarrativePort` | 포트. 템플릿이든 모델이든 뒤에 숨는다 |
| `TemplateNarrativeAdapter` | **기본**. 모델 없이 사실을 시간순으로 잇는다 |
| `OllamaNarrativeAdapter` | 로컬 모델. `NONE` 을 기권으로 받는다 |
| `TimelineNarrativeService` | 숫자 출처 검증(가드 1개) |
| `GET /api/v1/admin/orders/{orderNo}/narrative` | 읽기 전용 창구. 못 만들면 **204** |

**가드가 하나뿐인 이유**: 사내 화면에만 뜨고 상태를 바꾸지 않는다. 고객에게 안 나가므로
내부 용어 누출도 말투도 문제가 아니다. 남는 위험은 <b>없는 숫자를 만드는 것</b> 하나뿐이라
가드도 그 하나만 뒀다. 필요 없는 곳에 가드를 늘리면 무엇이 왜 있는지 흐려진다.

**버린다, 고치지 않는다.** 출처 없는 숫자가 하나라도 있으면 문단을 통째로 버린다.
틀린 숫자가 섞인 서술은 <b>없는 것보다 나쁘다</b> — 운영자가 그걸 근거로 확정하면 틀린 판단이
장부에 남는다. 상황 13 에서 조회 실패를 조용히 넘기지 않기로 한 것과 같은 이유다.

**못 만들면 204 다.** 빈 문자열이나 "생성 실패" 같은 문장을 돌려주면 화면이 그걸 서술로 띄운다.

## 4. 잰 것 — 템플릿 대비

잔여 후보를 끄면서 배운 기준을 <b>만들면서 바로</b> 적용했다. 절대 품질이 아니라
<b>기존 방식 대비</b>로 잰다. 여기서 기존은 모델 없는 템플릿이다.

같은 사실 10건을 둘에 태웠다. 재현: `./gradlew evalTest --tests '*NarrativeLiftEvalTest*'`

| | 출처 없는 숫자 | 기권 | 평균 길이 |
|---|---|---|---|
| 템플릿(기존) | 0건 | 0건 | 324자 |
| qwen3:8b | 0건 | 0건 | **232자** (-28%) |

숫자로는 **28% 짧아졌다**. 그런데 길이만으로는 판단이 안 되므로 문장을 봤다.

**템플릿**
```
주문 ORD-N000 — 2026-08-01 · ORDER · 주문 생성 10,000원 그다음 2026-08-01 · PAYMENT ·
결제 READY → IN_PROGRESS (USER, TOSS_PAYMENTS) 그다음 … 2026-08-02 · RECONCILIATION ·
대사 AMOUNT_MISMATCH (거래일 2026-08-02) — 내부 10,000 / 외부 9,700.
```

**qwen3:8b**
```
주문번호 ORD-N000은 2026-08-01에 주문 생성 후 결제 상태가 READY에서 IN_PROGRESS로
변경되었고, 이후 DONE 상태로 변경되었습니다. 결제 완료 후 원장에 10,000원이 기록되었습니다.
2026-08-02에 대사 상태가 AMOUNT_MISMATCH로 변경되었으며, 내부 거래금액은 10,000원,
외부 거래금액은 9,700원으로 불일치했습니다.
```

**차이가 분명하다.** 템플릿은 목록에 접속사만 붙인 것이라 <b>원래 목록보다 읽기 어렵다</b>.
모델 쪽은 상태 전이를 문장으로 잇고 날짜를 한 번만 말한다. 상태 이름(`READY`,
`AMOUNT_MISMATCH`)은 그대로 남아 화면과 대조된다 — 운영자용으로 의도한 그대로다.

**이게 잔여 후보와 정확히 반대인 지점이다.** 거기서는 규칙이 이미 같은 답을 내고 있어서
모델이 동의하는 것 말고 할 게 없었다. 여기서는 규칙이 <b>문장을 못 쓴다</b>.

## 5. 만들고 나서 다시 봤더니 — 프롬프트 인젝션 표면

현업 개발자에게 "운영에 AI를 붙일 거면 **거버넌스와 보안**을 신경 쓰라, **AI가 활동할 수 있는
범위를 확실히 제약하고 통제 가능한 걸** 보여주라"는 조언을 받고 방금 만든 것을 다시 봤다.

**사실 묶음의 문장이 전부 코드가 만든 것이 아니었다.**

```java
// DomainContributors
"분쟁 접수 (%s) — %s".formatted(d.chargebackId(), d.reason())
```

`reason` 은 **카드사가 보낸 웹훅 페이로드**에서 온다(`ChargebackWebhookController`).
그 값이 타임라인 요약에 실려 `FactPack` 을 거쳐 **모델 프롬프트까지 그대로 간다.**
`docs/11` 이 이미 경고해 둔 자리였다 — "상품명·`resolveNote`·분쟁 사유가 전부 자유 텍스트다".
경고는 적어 뒀는데, **정작 프롬프트를 만들 때 그걸 안 봤다.**

### 무엇을 했나

`UntrustedText.flatten` 을 두고 프롬프트에 실리는 사실 문장을 전부 통과시킨다.
서술·잔여 후보·상담 초안 **셋 다** 같은 사실 묶음을 쓰므로 표면이 같다.

- 개행·제어문자를 공백으로 → **줄바꿈으로 목록 구조를 깨지 못한다**
- 연속 공백 축약, 200자 상한 → **긴 문장으로 앞의 지시를 밀어내지 못한다**

**내용은 검열하지 않는다.** 무엇이 위험한 문장인지 판정하려 들면 그 판정이 또 틀린다.
여기서 지키는 것은 <b>구조</b>뿐이다 — 한 줄은 한 줄로 남게 한다.

### 이걸로 막히지 않는다

완벽 차단이 불가능하다는 것은 업계의 공통 인정이다. 여기서 한 일은 **가장 싼 표면을 없앤 것**뿐이다.

**진짜 방어선은 권한이다.**

| | |
|---|---|
| 쓰기 권한 | **없다** — 서술은 상태를 바꾸지 않는다(ADR-008) |
| 출력이 가는 곳 | 사내 화면. 고객에게 안 나간다 |
| 사람이 보는 방식 | **원본 사실 목록과 나란히** 본다 |
| 숫자 | 출처에 없으면 문단째 버린다 |

뚫려도 할 수 있는 것이 **사람에게 거짓말하는 것**까지이고, 장부는 못 바꾼다.
막는 것이 아니라 **뚫린다고 가정하고 권한을 설계한다.**

## 6. 재는 방법을 바꿨다 — 길이는 품질이 아니었다

4절에서 길이·기권·출처 없는 숫자로 쟀다. 앞의 둘은 품질이 아니고, **특히 길이를 개선으로 읽은
것은 방향이 틀렸다.** 평가자가 <b>긴 답을 선호하는 편향</b>은 이미 알려져 있어서, 짧아진 것을
좋아졌다고 읽을 근거가 없다. 편향을 반대로 뒤집어 해석한 셈이다.

### 업계 표준은 쌍 비교다

둘을 나란히 놓고 고르게 하는 **쌍 비교(pairwise)** 가 절대 점수보다 사람 판단과 잘 맞는다는 것이
알려져 있고, 프롬프트·모델을 A/B 로 견줄 때 쓰는 방식이 이것이다(Chatbot Arena·MT-Bench 계열).
절대 점수는 회귀 감시에 쓰고, **A/B 비교에는 쌍 비교**를 쓴다.

알려진 편향은 셋이고, 셋 다 설계로 막았다.

| 편향 | 어떻게 막았나 |
|---|---|
| 긴 답 선호 | **길이를 지표에서 뺐다** |
| 제시 순서 | 순서를 무작위로 하고 **그 순서를 함께 저장**한다(`source_a`/`source_b`) |
| 출처를 알면 기운다 | 고르기 전에는 **어느 쪽이 모델인지 안 보여준다** |

동점(`TIE`)을 허용한다. 억지로 고르게 하면 그 선택은 신호가 아니다.

```
POST /admin/orders/{orderNo}/narrative/compare   → A/B 두 문단 (출처 없음)
POST /admin/orders/narrative/compare/{id}        → 고른다. 고른 뒤에야 출처 공개
GET  /admin/orders/narrative/compare/stats       → 집계
```

**이 표가 쌓인 다음에 기본값을 정한다.** 그 전에는 안 바꾼다.

## 7. 거버넌스 — 무엇을 남기고 무엇을 못 하게 하나

프롬프트 인젝션은 **막는 것이 아니라 담는 것**이라는 쪽으로 업계 기준이 옮겨갔다.
2026년 판 OWASP LLM Top 10 도 프롬프트 인젝션을 1위에 그대로 두면서 초점을
<b>예방에서 봉쇄로</b> 옮겼다 — "모델은 속는다"를 전제로 깔고, 최소 권한·도구 허용 목록·
입출력 필터링·민감한 동작에 사람 승인·감사 로그를 권한다.

| 권고 | 여기서 |
|---|---|
| 외부 내용을 지시와 **분리해 제시** | 사실 목록을 `<<<사실 … 사실>>>` 경계에 넣고, 그 안은 데이터라고 명시 |
| 입력 필터링 | `UntrustedText.flatten` — 개행·제어문자 제거, 200자 상한 |
| 출력 필터링 | 숫자 출처 검증. 출처 없는 숫자가 하나라도 있으면 **문단째 버린다** |
| **최소 권한** | 쓰기 권한 없음. 읽기 전용(ADR-008) |
| 사람 승인 | 확정은 사람이 한다. 서술은 **참고 문장**일 뿐이다 |
| **감사 로그** | `narrative_audits` — 모델 이름·출력·판정·사실 개수·시각 |

### 감사 로그에서 무엇을 안 남기나

**프롬프트 본문은 저장하지 않는다.** 사실 묶음에서 결정적으로 재구성되기 때문이다.
대신 **사실 개수와 완전성 플래그**를 남겨 그때와 지금이 같은 입력인지 대조한다.

재구성되는 것을 또 저장하면 두 곳이 언젠가 갈라지고, 갈라지면 어느 쪽이 맞는지 알 수 없다 —
허용 금액 목록에서 이미 겪은 실패다.

**버린 것도 남긴다.** 화면이 빈 이유를 나중에 답할 수 있어야 하고, 폐기율 자체가 이 기능의
상태를 말한다.

## 8. 심판 모델로 1차 신호를 만들어 봤다 — 신호가 안 나왔다

사람이 고른 표본이 0건이라 켜지 못하고 있었다. 업계 관행이 <b>심판 모델로 대부분을 재고
사람은 보정과 엣지 케이스만 본다</b>는 것이라, 1차 신호라도 만들어 보기로 했다.

**심판을 다른 계열 모델로 세웠다.** 자기선호 편향은 잘 알려져 있다 — 심판과 생성자가 같은
모델이거나 같은 계열이면 자기 출력을 후하게 준다. 그래서 서술은 `qwen3:8b` 가 쓰고 심판은
`llama3.1:8b` 가 봤다.

**순서를 뒤집어 두 번 물었다.** 위치 편향도 알려져 있어서, A/B 를 바꿔 두 번 묻고
<b>답이 뒤집히면 동점</b>으로 셌다. 순서를 바꿨다고 답이 바뀌면 그건 선호가 아니다.

```
템플릿 0 · 모델 0 · 동점 8  (그중 순서 뒤집힘 8)
```

**여덟 건 전부 뒤집혔다.** 심판이 고른 것은 서술의 질이 아니라 <b>앞에 놓인 쪽</b>이었다.

### 그래서 이 심판은 못 쓴다

순서를 안 뒤집었으면 8:0 이든 0:8 이든 <b>깨끗한 숫자가 나왔을 것이고, 그걸 근거로 켰을
것이다.</b> 편향 대책을 설계에 넣어 둔 덕에 그게 신호가 아니라는 걸 알았다.

이것도 이 프로젝트에서 두 번째다 — <b>잣대가 나를 속이려 한 자리</b>가 또 나왔다.
상담 초안에서 채점 기준이 네 번 속였고, 여기서는 심판의 순서 편향이 속이려 했다.

**기본값은 그대로 `template` 이다.** 그리고 이제 이유가 더 정확해졌다 — 표본이 없어서가
아니라, <b>모델 심판으로는 이 차이를 못 가린다</b>는 것을 확인해서다. 사람이 골라야 한다.

### 이건 알려진 현상이고, 대책도 알려져 있다

나중에 문헌을 찾아보니 위치 편향은 널리 보고돼 있다. 순서만 바꿔도 <b>최대 30% 가 반전</b>되고
평균 order-flip 이 <b>0.236</b> 이다. 그리고 표준 완화책이 정확히 내가 한 것이다 — <b>양쪽 순서로
돌려 순서 의존 판정을 무승부로 처리</b>하면 위치 편향 신호가 거의 0 이 된다.

그래서 결론을 이렇게 다시 쓴다. <b>"뒤집혀서 못 쓴다"가 아니라 "표준 완화책을 적용했더니
8건 전부 무승부라 심판이 신호를 0 으로 준다"</b>다. 앞의 문장은 완화책을 모르고 한 말로 읽힌다.

## 9. 남는 것

- **쌍 비교 표본이 아직 0건이다.** 장치는 만들었지만 사람이 앉아서 골라야 채워진다.
  그래서 기본값은 여전히 `template` 이다.
- **필요한 표본 수를 근거 없이 잡고 있었다.** "몇 건이면 되나"를 정하지 않은 채 "쌓이면 정한다"고만
  적어 뒀다. 문헌을 찾으니 인간 선호 평가는 <b>50건이면 충분하고, 차이가 뚜렷하면 25~50건</b>에서
  승자가 드러난다. 그래서 승격 기준을 <b>최소 25건, 목표 30건</b>으로 못 박는다.
- **어노테이터가 한 명이다.** 표준은 인스턴스당 3~5명이고 그래야 평가자 간 일치도를 잴 수 있다.
  혼자 고른 30건으로는 <b>일치도를 못 재므로</b>, 이 결과는 "한 사람의 일관된 선호"까지만 주장한다.
- **사실 줄 단위로 신뢰도를 구분하지 않았다.** 지금은 목록 전체를 데이터 경계에 넣는다.
  분쟁 사유(외부)와 결제 상태 전이(코드)가 같은 `- ` 줄로 섞여 있다. 줄마다 출처를 표시하면
  모델이 구별할 수 있지만, 그러려면 타임라인이 신뢰도를 함께 내야 한다.
- **표본이 합성이다.** 실제 타임라인이 내는 문장 형식은 그대로 썼지만 값은 만든 것이다.
  실데이터로 다시 재야 한다.
- **기본은 여전히 template 이다.** 모델 쪽이 나아 보이지만, 사람이 읽고 판단한 표본 없이
  기본값을 바꾸지 않는다. 잔여 후보에서 그 순서를 어겼다가 되돌렸다.
- **한 모델만 봤다.** qwen3:8b 하나다. 모델을 키우면 나아지는지는 안 쟀다.
