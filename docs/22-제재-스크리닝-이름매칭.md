# 22. 이름 매칭으로는 못 가르는 자리가 있다

## 0. 왜 방향을 바꿨나

ADR-021 에 "AML 스크리닝을 안 붙인다"고 적고, 근거를 "신원을 안 갖고 있어서"라고 했다.
**그 근거의 절반이 틀렸다.**

| | 신원을 갖는 것이 범위 확장인가 |
|---|---|
| 구매자 | **맞다.** 국내 카드결제에 구매자 신원이 필요 없다 |
| 판매자 | **아니다.** 돈을 보내려면 <b>누구에게 보내는지 필연적으로 안다</b>. 사업자등록번호와 계좌 없이 정산할 방법이 없다 |

판매자 엔티티가 없던 진짜 이유는 개인정보 최소화가 아니라 <b>이 프로젝트가 단일 판매자
구조</b>여서다. 그리고 그 단순화 자체가 현실적이지 않다. 실제 정산은 누군가에게 한다.

## 1. 무엇을 만들었나

- `sellers` — 사업자등록번호·법인명·대표자명·국가·심사 상태(V36)
- `seller_screenings` — 판정마다 한 행. <b>지우지 않는다</b>
- `NameMatcher` — 정규화 + 편집 거리
- `SellerScreeningService` — 세 갈래 판정(CLEAR / POTENTIAL / CONFIRMED)

<b>판정 기록을 남기는 이유</b>: 제재 명단은 갱신된다. 어제 통과한 판매자가 오늘 걸릴 수 있고,
그때 "언제 무엇과 대조해 통과였는지"를 못 대면 규제 대응이 안 된다. 그래서 대조한 명단의
판(`list_version`)도 함께 남긴다.

## 2. 정규화로 지울 수 있는 것을 먼저 지웠다

표기 차이를 유사도에 맡기면 <b>임계를 낮춰야 하고 그만큼 오탐이 는다.</b> 먼저 지울 수 있는
것을 지우고, 남은 차이만 유사도로 본다. 대사 원인을 산수로 먼저 가른 것과 같은 순서다.

```
주식회사 한빛무역  ↔  한빛무역                  100   (법인격 표기)
Kim, Cheol-Su    ↔  Kim Cheol Su             100   (구두점·공백)
ＡＢＣ 무역        ↔  ABC 무역                 100   (전각·반각)
```

### 구두점을 한 갈래로 다루면 이름이 갈라진다

처음에 구두점을 전부 공백으로 바꿨다. 테스트가 잡았다.

```
O'Brien Michael  →  o brien michael      (붙어 있던 이름이 갈라진다)
OBrien Michael   →  obrien michael
                                          93 점. 같은 이름인데 100 이 아니다
```

이름 <b>안에</b> 들어가는 아포스트로피는 지우고, 이름을 <b>나누는</b> 하이픈·쉼표만 공백으로
바꾼다. 같은 구두점이라도 하는 일이 다르다.

## 3. 재 봤더니 못 가르는 자리가 나왔다

임계별로 오탐·미탐을 세려고 표본을 만들었다. 처음 표본에서는 모든 임계에서 0/0 이 나왔다.
<b>표본이 너무 쉬웠다.</b> 실제 오탐이 나오는 자리를 안 넣은 것이다.

같은 사람의 다른 로마자 표기와, 흔한 이름의 이웃을 넣었다.

```
같음   67  Kim Cheol Su ↔ Kim Chul Soo      (같은 사람, 다른 표기)
다름   67  김철수 ↔ 김철순                    (다른 사람)
```

<b>동점이다.</b> 임계를 어디에 둬도 이 둘은 안 갈린다. 이건 임계를 잘못 고른 것이 아니라
<b>편집 거리로는 못 하는 일</b>이다.

### 그래서 이 점수를 무엇으로 쓰나

<b>사람에게 보낼지 정하는 값</b>으로 쓴다. 맞고 틀림을 정하는 값이 아니다.

- 로마자 표기 차이는 음성학적 매칭(Soundex·Metaphone 계열)이 필요하다
- 동명이인은 <b>이름으로 못 가른다.</b> 생년월일·국적 같은 추가 식별자가 있어야 한다

이 한계를 모르고 임계만 조정하면 <b>오탐과 미탐을 맞바꿀 뿐</b>이다. 그게 이 실측의 결론이다.

## 4. 판정을 세 갈래로 둔 이유

통과와 차단만 두면 <b>애매한 것을 어느 한쪽으로 밀어야 한다.</b> 밀어서 통과시키면 제재
대상에게 돈이 가고, 밀어서 차단하면 멀쩡한 판매자의 정산이 묶인다. 애매한 것은 애매하다고
두고 사람에게 넘긴다.

<b>명단이 안 꽂혔으면 통과가 아니라 POTENTIAL 이다.</b> 안 본 것과 통과는 다르다. 기본
구현을 비워 둔 이유도 같다 — 명단을 저장소에 실으면 <b>낡은 명단이 코드와 함께 굳고</b>,
갱신 주기가 배포 주기에 묶이면 그것 자체가 규제 위반이 된다.

## 5. 정산을 판매자별로 다시 짰다

스크리닝만 만들고 정산이 집계인 채로 두면 <b>차단할 지급이 없다.</b> 그래서 이어서 했다.
이 키는 이미 한 번 조용히 틀려서 지급이 통째로 빠진 적이 있는 자리라 조심해서 갔다.

### 기존 주문에 가짜 판매자를 채우지 않았다

`seller_id` 를 `NULL` 허용으로 뒀다. 기존 주문은 <b>플랫폼이 직접 판 것</b>이고 그건 사실이다.
여기에 "플랫폼"이라는 판매자 행을 만들어 채우면 없던 판매자를 지어내는 것이 된다.
`NULL` 이 곧 직판을 뜻하고, 집계는 그것도 하나의 묶음으로 센다.

### 멱등 검사가 판매자별이어야 한다

전에는 <b>날짜만 보고</b> 정산이 있으면 항목 조회도 없이 건너뛰었다. 판매자를 넣으면 그게
못 쓴다. 나중에 등록된 판매자의 항목이 있어도 <b>날짜 정산이 이미 있다는 이유로 영영 안
나간다.</b>

그래서 순서를 뒤집었다. 항목을 먼저 모아 어떤 판매자가 있는지 알고, 판매자별로 존재를 본다.
재실행 때 조회가 한 번 더 도는 것이 그 대가다.

```java
Map<Long, List<SettlementItem>> bySeller = new HashMap<>();
for (SettlementItem item : all) {
    bySeller.computeIfAbsent(item.getSellerId(), k -> new ArrayList<>()).add(item);
}
```

<b>`Collectors.groupingBy` 를 못 쓴다.</b> `HashMap` 은 `null` 키를 허용하지만 `groupingBy` 가
맵에 넣기 전에 키를 검사해 거부한다. 처음에 그걸 모르고 썼다가 <b>기존 정산 테스트가 전부
깨졌다.</b> 돈 경로라 이런 것이 조용히 지나가면 안 되는데, 기존 테스트가 잡았다.

### NULL 은 유니크 제약이 안 지킨다

MySQL 유니크 인덱스는 `NULL` 을 서로 다른 값으로 본다. `(settlement_date, currency, seller_id)`
에 유니크를 걸어도 <b>플랫폼 직판 정산이 같은 날짜에 여러 개 생기는 것을 제약이 못 막는다.</b>
존재 검사 질의가 `seller_id is null` 을 따로 다뤄 함께 지킨다. JPA 파생 질의는 `= null` 로
만들어져 아무것도 못 찾으므로 직접 썼다.

## 6. 안 한 것
- <b>음성학적 매칭을 안 붙였다.</b> 3절의 한계를 확인만 하고 해결은 안 했다.
  붙이려면 한국어 이름의 로마자 표기 규칙부터 정해야 한다
- <b>실제 명단으로 재지 않았다.</b> 매칭 방식만 쟀다. 명단의 크기가 커지면 성능도 봐야 한다
