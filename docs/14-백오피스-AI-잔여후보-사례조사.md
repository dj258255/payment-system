## 왜 지금 만드나

[11 문서](11-AI-운영자동화-검토.md)가 정한 순서에서 ④만 남았다.

```
① 타임라인 조립기(AI 없음)  ✅  ADR-011
② 규칙 분류기(AI 없음)      ✅  ADR-012
③ CS 답변 초안(AI)          ✅  ADR-014
④ 잔여 원인 후보(AI)        ⬜  이 문서
```

그동안 ④를 미룬 이유는 "일치율이 쌓이기 전에는 나아졌다고 말할 수 없다"였다. 그 판단은
**운영 중인 시스템에는 맞지만 개인 프로젝트에는 안 맞는다.** 여기에는 쌓일 실데이터가
없고, 기다린다고 생기지도 않는다. 만들어서 재는 쪽이 배우는 게 많다.

다만 **"만들었다"와 "쓸 만하다"를 섞지 않는다.** 아래 조사가 그 선을 어디에 그을지에 대한 것이다.

## 해외 사례

### Ramp — 거래 재분류 에이전트 (가장 가까운 사례)

카드 거래가 엉뚱한 가맹점으로 분류됐을 때 이를 고치는 에이전트다. 우리 ④와 구조가 거의 같다.
**분류 후보가 정해져 있고, 사람이 하던 예외 처리를 대신하며, 틀리면 돈에 영향이 간다.**

| 항목 | 내용 |
|---|---|
| 입력 | 카드 가맹점명, MCC, 영수증 이미지, 사용자 메모, 가맹점 임베딩 |
| 출력 | 세 가지 행동 중 하나(신규 생성 / 기존 수정 / 재배정) |
| 처리 시간 | 사람 수 시간 → **10초 미만** |
| 커버리지 | **1.5~3% → 거의 100%** |
| 거절률 | 요청의 **25%를 에이전트가 거절** |
| 후속 정정 요청 | **10% 미만** |

가져올 장치가 셋이다.

1. **후처리 가드레일**: 모델이 고를 수 있는 값을 **미리 정한 목록으로 제한**한다.
   Ramp의 표현으로는 "존재하지 않는 가맹점을 발명하는 것"을 막는 장치다.
2. **재시도**: 모델이 형식에 안 맞는 응답을 내면 무엇이 틀렸는지 알려주고 다시 시킨다.
3. **섀도 모드**: 에이전트가 "무엇을 할 것인지"만 정하고 실행하지 않는다. 실제 트래픽 위에서
   사람의 행동과 대조해 정확도를 누적하고, **임계를 넘은 뒤에야** 실제 개입을 켠다.

세 번째가 요점이다. 이 프로젝트는 상담 초안에 이미 `ShadowDraftRecorder`로 같은 것을 갖고 있다.
④에도 같은 방식을 쓰면 **"만들었다"와 "켰다"를 분리**할 수 있다.

### Modern Treasury — 결제 전용 AI 플랫폼 (2025-05)

대사 엔진에 AI를 붙여 **불일치에 사유 코드와 설명 문장을 붙인다.** 원시 예외 목록을 재무팀이
바로 처리할 수 있는 할 일 목록으로 바꾸는 것이 목적이다. 타이밍 차이인지 은행 수수료인지 같은
**맥락을 붙여주는 쪽**이지 종결까지 하는 쪽이 아니다.

이 프로젝트의 규칙 분류기가 이미 사유와 근거를 함께 낸다. ④는 **규칙이 아무 후보도 못 낸
잔여분**에만 같은 일을 하는 셈이다.

### 선택적 예측(selective prediction)과 기권(abstention)

고위험 분류에서 표준으로 쓰는 장치다. 신뢰도가 임계 아래면 **답을 내지 않는다.**
커버리지를 정확도와 맞바꾸는 것이고, 최근 연구는 기권을 "정답/오답/모름" 3분류로 두고
오답률에 상한을 거는 형태까지 간다.

④에 그대로 필요하다. **규칙이 못 가른 건은 애초에 어려운 건**이라 모델이 아무거나 고르면
사람의 일이 늘어난다. `OTHER`로 답하거나 근거를 못 대면 제안을 안 하는 게 낫다.

## 국내 사례

### 토스 — Flowise + LLM 에러 분석 자동화

운영 중 발생한 에러를 LLM이 분석하게 만든 사례다. 배운 점으로 **"더 많은 정보를 제공할수록
더 많은 분석을 이끌어낼 수 있었다"**를 든다. ④에서 `OrderTimeline`을 통째로 넘기는 근거가 된다.
사실이 부족한 상태로 물으면 모델은 추측으로 메운다.

### 카드사 FDS — 사람의 일이 바뀐다

신한카드를 비롯한 카드사가 FDS에 AI를 적용하고 있다. 정리된 서술이 이 프로젝트의 방향과 같다.
**기본 분류·대조·반복 입력은 AI가 처리하고, 담당자는 이상 수치·예외 케이스·고위험 건 같은
판단이 필요한 업무에 집중한다.**

④의 자리가 정확히 그 반대편이라는 점이 중요하다. 이 프로젝트에서 **기본 분류·대조는 이미
규칙이 한다.** AI에게 남는 건 규칙이 못 가른 어려운 건이고, 그건 판단이 필요한 쪽에 가깝다.
그래서 **제안까지만** 한다.

### 금융위 생성형 AI 활용 지원방안

망분리 규제가 [ADR-014](adr/ADR-014-cs-draft-port-and-number-guard.md)에서 포트를 먼저 만든
이유였다. ④도 같은 포트 구조를 쓴다. 어댑터를 바꿔 로컬 모델과 외부 API를 갈아끼운다.

## 설계

### 계약

```
ResidualCausePort
  입력  ReconciliationResult + OrderTimeline + 규칙이 낸 제안 목록(비어 있음)
  출력  ResidualSuggestion(cause, rationale, confidence)  또는  기권
```

### 여섯 개의 가드

| # | 가드 | 근거 |
|---|---|---|
| 1 | **규칙이 아무것도 못 냈을 때만 호출** | 산수가 답하는 걸 추측하게 만들지 않는다 |
| 2 | **출력은 `ResolveCause` enum 값만** | Ramp 후처리 가드레일. 없는 원인을 발명 못 하게 |
| 3 | **`SUSPECTED_TAMPERING`은 제안 금지** | 11 문서의 "항상 사람" 원칙. 위변조는 유형으로 배제 |
| 4 | **신뢰도 임계 미만이면 기권** | selective prediction. `OTHER`도 기권으로 친다 |
| 5 | **근거 문장의 숫자는 `NumericProvenanceGuard`로 검증** | 이미 있는 장치를 재사용. 지어낸 숫자면 통째로 버린다 |
| 6 | **`resolve`는 절대 안 한다** | 자동 확정은 이 단계의 범위가 아니다 |

가드 5가 이 프로젝트만의 것이다. Ramp는 가맹점 목록으로 출력을 제한했는데, 우리는 원인 코드뿐
아니라 **근거 문장에 나오는 금액과 날짜까지** 코드가 낸 값인지 대조한다. 상담 초안에서 만든
장치가 그대로 쓰인다.

### 섀도 모드부터

만들자마자 화면에 띄우지 않는다. 제안을 기록만 하고, 사람이 확정한 원인과 대조해 일치율을
누적한다. 이 프로젝트에는 라벨이 사람의 확정 순간에 생기므로 이미 그 자리가 있다.

**그리고 이 수치도 "정확도"가 아니다.** 섀도 모드에서는 사람이 제안을 못 보므로 앵커링 편향은
없지만, 표본이 손으로 만든 대사 케이스라 분포가 실제와 다르다. 그래서 **"탐색 실행의 일치율"**로
부른다.

### 무엇을 재나

| 지표 | 왜 |
|---|---|
| 기권률 | 높으면 만든 의미가 없다. Ramp의 거절률 25%가 참고점 |
| 자동 매칭률 | 업계는 초기 75~85%, 성숙하면 95% 이상. 예외 큐가 전체의 5~15%로 줄어든다.\n  ④가 맡는 자리는 그 예외 큐의 <b>안쪽</b>이다 |
| 커버리지 | 규칙이 못 가른 것 중 몇 %에 후보를 냈나 |
| 일치율 | 후보를 낸 것 중 사람의 확정과 몇 %가 같았나 |
| 가드 5 폐기율 | 지어낸 숫자로 버려진 비율 |

기권률과 일치율은 맞바꾸는 관계라 **둘을 같이 봐야 한다.** 하나만 보면 "아무것도 제안 안 하는
안전한 모델"이 최고가 된다.

## 만들고 재봤다

대사 케이스 **12건**을 손으로 만들었다. 아홉은 정답이 있는 건이고 셋은 **기권해야 맞는 건**이다.
원인 일곱 종을 모두 덮는다. 모델은 같은 계열의 크기 차이(qwen3 8B·14B)와 **다른 계열**
(llama3.1 8B)을 같이 본다. 계열 편향과 크기 효과를 갈라야 하기 때문이다.

### 원인 코드에 뜻을 줬을 때와 안 줬을 때

| 모델 | 이름만 | 정의 있음 | 차이 |
|---|---|---|---|
| qwen3:8b | 6 / 12 | **9 / 12** | +3 |
| qwen3:14b | 7 / 12 | **12 / 12** | +5 |
| llama3.1:8b | 3 / 12 | **8 / 12** | +5 |

세 모델 모두 올랐다. 계열이 다른 llama 도 같은 폭으로 올랐으니 특정 모델의 성질이 아니다.
**모델을 키운 것보다 정의를 붙인 게 컸다.** 8B에서 14B로 키운 효과가 1차에서 +1인데,
정의를 붙인 효과는 같은 8B에서 +3이다.

1차에서 틀린 자리가 모델을 넘어 겹쳤다. `TIMEZONE_BOUNDARY`와 `PG_FILE_DELAY`는 둘 다
"다른 날짜 파일에 있다"라서 **방향을 알려주지 않으면 가를 수 없다.** 이름만 보고 가를 수
있다고 여긴 것이 잘못이었다.

이건 알려진 현상이다. 분류 과제에서 카테고리 설명을 뺐을 때 Micro F1 이 0.79에서 0.73으로
떨어졌다는 절제 실험이 있고, 라벨링 규칙을 요약해 넣자 F1 이 0.57에서 0.95로 올랐다는
보고도 있다.

### 가드 4의 전제를 재봤다

"신뢰도가 낮으면 틀릴 가능성이 높다"가 가드 4의 전제다. 원인을 실제로 고른 건만 모아
맞은 답과 틀린 답의 평균 신뢰도를 비교했다. **기권은 뺐다** — 기권 정답의 신뢰도가 0이라
섞으면 평균이 왜곡된다.

| 모델 | 맞은 답 | 틀린 답 | 차이 |
|---|---|---|---|
| qwen3:8b | 90 | 87 | +3 |
| qwen3:14b | 88 | (틀린 답 0건) | 잴 수 없음 |
| llama3.1:8b | 83 | **85** | −2 |

**두 분포가 겹친다.** llama3.1 은 틀린 답의 신뢰도가 오히려 높다. 임계 70을 걸어도 양쪽 다
통과하고, 85로 올리면 맞은 답까지 같이 떨어진다. **가드 4는 사실상 안 걸린다.**

이것도 알려진 현상이다. 말로 표현한 신뢰도(verbalized confidence)는 경험적으로 보정이
안 돼 있다. 원인으로 지목되는 것 중 하나가 RLHF 인데, 보상 모델이 단정적으로 들리는 답을
선호해서 학습된 모델이 마땅히 해야 할 만큼 유보하지 않는다.

**모델에게 자기 확신을 물어 거르는 설계는 처음부터 약했다.** 문헌이 이미 말하고 있던 것을
안 찾아보고 넣었다.

### 오답 하나가 가드를 전부 통과한다

2차에서 qwen3:8b 가 못 맞힌 셋 중 하나가 기권해야 하는 건이었다.

```
사실:  결제 승인 25,000원 / 금액 불일치, 차액 7,000원
8b :   FEE_CALCULATION_DIFF, confidence 80
14b:   ABSTAIN, confidence 0
```

7,000원이 수수료율과 맞는다는 근거가 어디에도 없다. 그런데 이 응답은 **가드 다섯 개를 전부
통과한다.** 원인 코드는 목록 안이고, 금지 유형도 아니고, 신뢰도 80은 임계 70을 넘고,
근거에 쓴 7,000원은 사실에 있는 값이라 숫자 검증기도 통과한다.

**출처가 맞는 숫자로 틀린 주장을 할 수 있다.** 지어낸 숫자가 아니라 있는 숫자를 틀린 인과에
붙인 것이다. 그 층은 검증기가 아니라 채점 기준이 맡는데,
[12편에서 그 잣대가 네 번 속였다](https://dj258255.github.io/IT-Oasis/blog/project/pay/pay-ch11-ruler-fooled-me/).

### 화면까지는 연결했는데 경계에 한 번 걸렸다

만들고 껐다로 끝내면 "만들었다"도 아니다. 그래서 사람이 보는 화면까지 연결했다.
그런데 확정 화면 쪽에서 부를 수가 없었다.

```
reconciliation   allowedDependencies = { shared, payment, audit }
assist           allowedDependencies = { shared, timeline, reconciliation }
```

`ReconciliationAdminService`가 `assist`를 부르면 **순환**이다.
[10편이 "경계를 지키느라 못 막은 구멍"](https://dj258255.github.io/IT-Oasis/blog/project/pay/pay-ch8-reconciliation-judgement/)이라고
적은 자리와 정확히 같다.

그래서 창구를 `assist` 쪽에 두고 **화면이 두 번 부르게** 했다.
`GET /api/v1/admin/orders/{orderNo}/residual-cause`다. 상담 초안도 이미 같은 구조다.
왕복이 하나 늘지만 경계가 유지되고, **규칙 제안만으로 충분한 건에서는 이 호출이 아예 안 나간다.**

응답에 `source`를 항상 싣는다. 규칙이 낸 후보와 모델이 낸 후보가 화면에서 같아 보이면
사람이 둘을 같은 무게로 읽는다. 그러면 가드를 여섯 개 걸어둔 의미가 화면에서 사라진다.

### 그래서 아직 "자동화됐다"고 말하지 않는다

지금 상태를 정확히 적으면 이렇다. **장치는 다 만들었고, 화면 창구도 있고, 재봤다.**
그런데 기본값이 꺼짐이고, 켜도 하는 일은 **후보 하나를 더 얹는 것**이다. 확정은 사람이 한다.

Ramp도 같은 순서로 갔다. 섀도 모드로 사람의 행동과 대조하다가 임계를 넘은 뒤에 실제 개입을 켠다.
켜는 조건은 셋이다.

1. **기권률과 일치율을 같이 본다.** 하나만 보면 아무것도 제안 안 하는 모델이 최고가 된다
2. **표본이 6건이다.** 손으로 만든 것이라 분포가 실제와 다르다. 이 수치는 탐색 실행이지 평가가 아니다
3. **신뢰도를 임계로 쓰는 것 자체가 검증되지 않았다.** 틀린 답에 80~90이 나온다.
   보정(calibration) 없이는 가드 4가 사실상 안 걸린다
