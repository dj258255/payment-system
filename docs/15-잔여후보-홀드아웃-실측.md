# 잔여 후보 — 홀드아웃 실측 (2026-09-05)

문서 `14-백오피스-AI-잔여후보-사례조사.md` 가 남긴 한계를 닫으려고 다시 쟀다.

> 91~100%는 **기준을 고친 그 표본에서 다시 잰 값**이다. 엔진이 만든 표본은 개발과
> 홀드아웃으로 나누지 않았다.

기준을 그 표본을 보고 고쳤으니 그 표본에서 잘 나오는 것은 당연하다. "쓸 만하다"의 근거로는
약한 수치였다.

---

## 1. 어떻게 쟀나

**프롬프트는 한 글자도 안 바꿨다.** 케이스만 새로 만들었다.

- 시드 `20260905` 로 45건 생성. 기준을 고칠 때 쓰이지 않은 표본이다.
- 사실 문장은 지어내지 않고 실제 형식을 그대로 썼다 —
  `DomainContributors` 가 대사 결과를 옮길 때 쓰는
  `"대사 %s (거래일 %s) — 내부 %s / 외부 %s"` 와 `FactPack` 의 `"날짜 · 출처 · 요약"`.
  값만 새로 뽑았다.
- 세 유형을 15건씩 만들었다.

| 유형 | 사실 | 정답 |
|---|---|---|
| `EXTERNAL_ONLY` | 내부 없음 / 외부 있음 | `INTERNAL_RECORD_LOST` |
| `AMOUNT_MISMATCH` | 내부·외부 둘 다 있고 금액만 다름 | 기권 |
| `INTERNAL_ONLY` | 내부 있음 / 외부 없음 | 기권 |

정답이 저렇게 갈리는 이유는 켠 유형이 하나뿐이기 때문이다. 판정 기준이
"내부 기록 금액이 아예 없을 것"이므로 `EXTERNAL_ONLY` 만 그 값이고 나머지는 전부 기권이다.

재현: `./gradlew evalTest`. Ollama 와 모델 3종이 필요해 기본 스위트에서는 제외했다.

## 2. 결과 — 91~100% 는 재현되지 않았다

| 유형 | 정답 | qwen3:14b | qwen3:8b | llama3.1:8b |
|---|---|---|---|---|
| `EXTERNAL_ONLY` | `INTERNAL_RECORD_LOST` | **15/15** | **15/15** | **15/15** |
| `AMOUNT_MISMATCH` | 기권 | 15/15 | **0/15** | 10/15 |
| `INTERNAL_ONLY` | 기권 | **0/15** | **0/15** | **0/15** |
| **전체** | | **67%** | **33%** | **56%** |

### 살아남은 것

**켠 유형은 세 모델 모두 15/15 다.** 홀드아웃에서도 100%가 유지됐다. 이 부분의 주장은
표본을 바꿔도 성립한다.

### 무너진 것

**기권해야 할 건에서 무너진다.** 특히 `INTERNAL_ONLY` 는 세 모델 모두 **0/15** 다.
프롬프트에 이렇게 적어 뒀는데도 그렇다.

```
  - 내부 기록 금액이 <있으면> 이 원인이 아닙니다. 반드시 ABSTAIN 입니다
```

방향이 정반대인데 같은 값을 낸다. `14-` 문서의 0/40 과 같은 실패이고,
**판정 기준을 명시한 뒤에도 안 고쳐졌다.**

## 3. 이 오답은 기존 가드가 못 막는다

프롬프트가 **켠 유형만** 보여주므로(`causeMenu()` 가 `ENABLED` 로 거른다) 모델이 낼 수 있는
값은 `INTERNAL_RECORD_LOST` 아니면 기권 둘뿐이다. 그래서 **모든 오답이 켠 유형과 같은 값**이다.

| 가드 | 막나 | 왜 |
|---|---|---|
| 가드 1 (규칙이 이미 답함) | ✗ | `classifyInternalOnly` 의 폴백은 `likely` 인데 가드 1은 `DECISIVE` 만 막는다 |
| 가드 7 (켠 유형인가) | ✗ | 오답이 곧 켠 유형이다 |
| 가드 4 (신뢰도 ≥ 70) | ✗ | 이 오답들의 신뢰도는 95~100 이었다 |

**즉 틀린 후보가 운영자 화면까지 나간다.** 기본 모델이 `qwen3:8b` 였으므로 45건 중 30건이다.

## 4. 고친 것

### 가드 8 — 판정 기준을 코드로도 강제한다

```java
if (s.cause() == ResolveCause.INTERNAL_RECORD_LOST && !facts.internalRecordAbsent()) {
    count("contradicts_recon_result");
    return Optional.empty();
}
```

이 프로젝트가 이미 배운 것을 한 번 더 적용한 것이다 — **프롬프트로 지시하고, 코드로도 막는다.**
지시만 하면 모델이 어긴다.

신호는 문장에서 되뽑지 않는다. `FactPack` 이 `internalRecordAbsent` 를 **구조화된 값으로** 함께
낸다(`RECON_EXTERNAL_ONLY` 항목이 타임라인에 있는가). 문장 `"내부 없음"` 을 정규식으로 뽑으면
문구를 고칠 때 가드가 조용히 깨진다 — 허용 목록에서 이미 한 번 겪은 실패다.

### 기본 모델 교체

`qwen3:8b` → `qwen3:14b`. 홀드아웃에서 33% 대 67% 였다.

## 5. 재측정 — 그리고 100%가 무엇 덕인지

같은 45건에 가드 8을 태웠다.

| 유형 | 정답 | qwen3:14b | qwen3:8b | llama3.1:8b |
|---|---|---|---|---|
| `EXTERNAL_ONLY` | `INTERNAL_RECORD_LOST` | 15/15 → **15/15** | 15/15 → **15/15** | 15/15 → **15/15** |
| `AMOUNT_MISMATCH` | 기권 | 15/15 → **15/15** | 0/15 → **15/15** | 10/15 → **15/15** |
| `INTERNAL_ONLY` | 기권 | 0/15 → **15/15** | 0/15 → **15/15** | 0/15 → **15/15** |
| **전체** | | 67% → **100%** | 33% → **100%** | 56% → **100%** |

**이 100%는 모델이 좋아진 것이 아니다.** 가드 8이 기계적으로 바꾼 값이다. 모델이 낼 수 있는
값은 `INTERNAL_RECORD_LOST` 아니면 기권 둘뿐이고, 가드 8은 그 값을 대사 결과가
<외부에만 있음>일 때만 통과시킨다. 그래서 기권해야 할 두 유형은 **구조적으로** 100%가 된다.

수치로 의미가 있는 칸은 `EXTERNAL_ONLY` 하나뿐이고, 거기서 세 모델이 15/15 다.

## 6. 그런데 그 한 칸도 모델이 필요 없다

`CauseClassifier` 를 다시 보니 이렇게 돼 있다.

```java
case EXTERNAL_ONLY -> out.add(CauseSuggestion.likely(ResolveCause.INTERNAL_RECORD_LOST,
        "외부에만 존재. 내부에 이 주문의 기록이 없다"));
```

**규칙이 이미 같은 답을 낸다.** 대사 결과 유형만 보고 결정된다.

정리하면 이렇다.

- 모델이 낼 수 있는 값 = `INTERNAL_RECORD_LOST` 또는 기권
- 그 값이 통과하는 조건(가드 8) = 대사 결과가 `EXTERNAL_ONLY`
- 그 조건에서 규칙이 내는 값 = `INTERNAL_RECORD_LOST`

**지금 켠 범위에서 모델이 할 수 있는 최선은 규칙에 동의하는 것뿐이다.** 그 왕복은 값을
만들지 않고 지연과 비용만 만든다. 그래서 가드 1-1 을 뒀다 — 규칙이 이미 켠 유형을 제안하면
모델을 부르지 않는다.

```java
if (rules != null && rules.stream().anyMatch(r -> ENABLED.contains(r.cause()))) {
    count("rules_already_cover");
    return Optional.empty();
}
```

### 남는 질문

이 기능을 켜 둘 이유가 남아 있는가. 지금 상태로는 **모델이 도달할 수 있는 자리가 없다.**
유형을 하나 더 여는 것(그 유형의 실측 정확도를 먼저 확보해서)이 아니면, 끄는 것이 정직하다.
`14-` 문서의 유형별 표를 보면 나머지 유형은 세 모델 모두 0~50% 라 지금은 열 수 없다.

## 7. 결정 — 껐다

`app.assist.residual-provider` 기본값을 `ollama` → `template` 으로 되돌렸다.
평가 하네스(`./gradlew evalTest`)와 가드 8·1-1 은 남겨 둔다. 규칙이 못 가르는 유형을
열 수 있게 되면 그때 다시 켠다.

### 현업 기준으로도 이게 맞다

**후보를 올리는 기준은 절대 정확도가 아니라 기존 방식 대비 개선(lift)이다.** LLM을 프로덕션에
올릴 때 표준 절차가 섀도 모드로 후보와 현행을 같은 입력에 태워 비교하고, 그 차이로 승격을
정하는 것이다. 여기서 현행(baseline)은 규칙 분류기이고, 측정된 차이는 **0** 이다.

대사 자동화에서 규칙과 ML을 섞는 것은 표준이지만, 나누는 기준이 있다 —
**결정적으로 갈리는 건은 규칙, 모호하고 편차가 큰 건은 모델.** 지금 켠 유형은 대사 결과 유형
하나로 결정되는 건이라 애초에 모델의 자리가 아니었다.

`14-` 문서가 유형별로 갈라 잰 것까지는 맞았다. 놓친 것은 **그 유형을 규칙이 이미 답하고 있다**는
사실이었다. 정확도를 유형별로 보면서 <규칙 대비>로는 안 봤다.

### 무엇이 남았나

기능은 껐지만 이 과정에서 만든 것은 남는다.

- **재현 가능한 평가 하네스** — 전에는 애드혹이라 다시 못 돌렸다
- **가드 8** — 판정 기준을 코드로 강제. 유형을 다시 열 때 필요하다
- **가드 1-1** — 규칙이 이미 답한 건에 모델을 부르지 않는다
- **홀드아웃 절차** — 다음에 유형을 열 때 이 방식으로 먼저 잰다
