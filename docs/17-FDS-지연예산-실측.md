# FDS 지연 예산 — 승인 경로에 넣을 수 있는가 (2026-09-05)

`docs/11` 이 스스로 이렇게 적어 뒀다.

> 승인 경로 실시간 서빙은 이미 표준이다 — 카카오뱅크 10ms, Stripe sub-100ms.
> pay가 안 하는 이유는 난이도가 아니라 **지연 예산을 재본 적이 없어서**다

> 지연 예산을 **한 번도 재본 적이 없다**

재본 적 없는 것을 근거로 설계를 정하고 있었다. 그래서 쟀다.

---

## 0. 먼저, 문서가 없는 기능을 있다고 말하고 있었다

`fraud/package-info.java` 가 이렇게 적고 있었다.

> 동일한 판정 엔진을 **두 결에서 재사용한다**: (1) **동기 인라인 판정**, (2) 비동기 사후 탐지

**(1)이 없다.** `FraudService.evaluate` 를 부르는 곳은 `FraudPostHocListener` 하나이고,
그것은 `PaymentConfirmedEvent` 를 받는 경로다. 결제가 <b>이미 끝난 뒤</b>에 다시 평가한다.

그래서 **`BLOCK` 판정이 결제를 막지 않는다.** 네 갈래를 계산은 하지만 REVIEW/BLOCK 은
심사 큐에 쌓이고 사람이 사후에 처리한다. 주석을 사실에 맞게 고쳤다.

부수 효과로 `docs/11` 표의 **홀드아웃 ❌** 항목은 지금 성립하지 않는다. Stripe 처럼
"일부러 통과시켜 오탐율을 재는" 장치가 필요한 이유는 <b>차단한 건의 정답을 모르기 때문</b>인데,
지금은 아무것도 안 막으므로 생존편향이 없다. 진짜 빈 곳은 라벨이 될 실데이터가 없다는 쪽이다.

---

## 1. 업계는 예산을 어떻게 잡나

| 기준 | 값 |
|---|---|
| 카드 결제 종단 | **p99 < 100ms** |
| 카드 비대면(이커머스) | **250~300ms** (넘으면 이탈이 는다) |
| 그중 부정거래 판정 몫 | **10~50ms** |
| 룰 엔진만 | 2~5ms |
| GBDT 모델을 REST 로 서빙 | 15~40ms |

그리고 **평균이 아니라 꼬리로 잡는다.** 평균 40ms 인데 피크에 800ms 로 튀는 시스템은
하필 부정거래가 몰릴 때 타임아웃 난다.

---

## 2. 잰 것 ① — 판정 한 번의 지연

실 Redis(Testcontainers)로 2,000회. 워밍업 200회 별도.
키를 매번 바꿔 잰다 — 같은 키만 두드리면 Redis 가 아니라 캐시 친화성을 재게 된다.

```
p50 1.19 ms   p95 1.53 ms   p99 1.92 ms   max 6.61 ms
```

이 판정은 Redis velocity 카운터를 **카드·기기·IP 로 세 번** 왕복한다.
그런데도 p99 가 2ms 아래다. 업계가 룰 엔진에 잡는 2~5ms 안에 든다.

재현: `./gradlew integrationTest --tests '*FdsLatencyBudgetTest*'`

## 3. 잰 것 ② — 승인 경로 종단

`k6/checkout-load.js`, 최대 50 VU, 반복 2,003회 / 요청 4,007건.

```
med 26.2 ms   p95 56.8 ms   p99 105.4 ms   max 384.6 ms   실패 0.00%
```

---

## 4. 그래서 답은

**넣을 수 있다.** 계산이 이렇게 된다.

| | 값 |
|---|---|
| 지금 승인 경로 p99 | 105.4 ms |
| FDS 판정 p99 | 1.9 ms |
| 넣었을 때 예상 p99 | **약 107 ms** |
| 이커머스 예산 | 250~300 ms |

**예산의 절반도 안 쓴다.** 판정이 차지하는 몫은 종단의 **약 1.8%** 다.

그동안 "지연이 붙으니까"를 이유로 사후 탐지에 둔 것인데, **그 이유가 숫자로는 성립하지 않는다.**
난이도도 지연도 아니었고, 그냥 재본 적이 없었던 것이다.

---

## 5. 그런데 지금 붙이지는 않았다

숫자가 된다고 바로 붙이는 것은 이 프로젝트가 피해 온 순서다. 붙이기 전에 정해야 할 것이 남았다.

- **Redis 가 죽으면 결제가 어떻게 되나.** 지금 `RedisVelocityCounter` 는 실패를 fail-open 으로
  흡수한다(이번 시도만 카운트). 사후 탐지에서는 그래도 되지만, 승인 경로에서는 그 선택이
  <b>부정거래를 통과시키는 결정</b>이 된다. 반대로 fail-close 하면 Redis 장애가 결제 장애가 된다.
- **`BLOCK` 이 실제로 막기 시작하면 오탐이 곧 매출 손실이다.** 그때부터 홀드아웃(일부러 통과시켜
  오탐율을 재는 장치)이 필요해진다 — 지금은 아무것도 안 막아서 필요 없던 것이다.
- **`CHALLENGE` 를 받을 곳이 없다.** 추가 인증 흐름이 없으므로 지금 이 등급은 이름만 있다.

즉 **막을 준비**가 판정 속도보다 큰 일이다. 이번에 닫은 것은 "지연 때문에 못 한다"는
근거 없는 이유 하나이고, 남은 것은 위 셋이다.
