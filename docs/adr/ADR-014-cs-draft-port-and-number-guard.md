# ADR-014 — 상담 초안: 포트를 먼저 만들고 모델은 나중에

- 상태: 채택 (Accepted)
- 관련: [ADR-011 타임라인 조립](ADR-011-order-timeline-assembly.md), [ADR-012 규칙 기반 원인 분류](ADR-012-rule-based-cause-classifier.md), [11 AI 운영자동화 검토](../11-AI-운영자동화-검토.md)

## 배경

[11 문서](../11-AI-운영자동화-검토.md)에서 만드는 순서를 정했다.

```
① 타임라인 조립기(AI 없음) → ② 규칙 분류기(AI 없음) → ③ CS 답변 초안(AI) → ④ 잔여 후보(AI)
```

①②는 끝났다(ADR-011, ADR-012). ③을 만들 차례인데, **모델을 부르는 코드를 지금 도메인에 박으면 안 되는 이유**가 조사 과정에서 나왔다.

## 왜 지금 모델을 부르지 않나

### 규제 — 생성형 AI는 아직 망분리 예외가 아니다

2026-04-20 시행된 **전자금융감독규정시행세칙** 개정으로, 금융회사·전자금융업자가 일정 보안 규율을 지키면 **내부 업무망에서 별도 혁신금융서비스 심사 없이 SaaS를 이용**할 수 있게 됐다.

**그런데 생성형 AI는 그 대상이 아니다.** 금융당국은 *"SaaS에 이어 향후 생성형 AI 서비스 도입 등과 관련해서도 (…) 신속히 망분리 규제 예외가 적용될 수 있도록 추진할 계획"* 이라고 밝혔다. 즉 **아직 열리지 않았고, 열릴 예정인 상태**다. 코어뱅킹 등 고객 개인신용정보를 직접 처리하는 시스템은 여전히 강한 망분리가 적용된다.

pay가 다루는 것은 주문번호·결제금액·취소이력이다. 결제 데이터를 외부 API로 내보내는 코드를 지금 도메인에 박아 두면, 규제가 열릴 때가 아니라 **지금** 문제가 된다.

### 평가 순서 — Klarna가 되돌린 이유

Klarna는 AI 상담으로 해결시간을 11분에서 2분으로 줄였다가 되돌렸다. CEO가 인정한 실패 원인은 기술이 아니라 **지표 설계 순서**였다.

> 비용이 지나치게 지배적인 평가 요소였고, 그래서 품질이 낮아졌다

업계 권고도 같다 — *"eval harness를 첫 주에 만들고, 모든 프롬프트·모델 변경을 그것으로 게이팅하라."* 모델을 고른 뒤 잣대를 만들면 **잣대가 그 모델에 맞춰 휜다.**

## 결정

**포트를 정의하고, 기본 구현은 외부 호출이 없는 템플릿으로 둔다. 평가 하네스를 모델보다 먼저 만든다.**

```
OrderTimeline + CauseSuggestion   ← 결정적으로 조립 (ADR-011, ADR-012)
        ↓
   FactPack                       ← 숫자·시각·상태만. 문장 없음
        ↓
   DraftPort                      ← 템플릿이든 모델이든 여기서 갈린다
        ↓
   NumberGuard                    ← 초안의 모든 금액·날짜를 FactPack과 대조
        ↓
   상담원이 검토·수정 후 발송      ← 초안은 고객에게 직접 나가지 않는다
```

### 새 모듈 `assist`

`allowedDependencies = { shared, timeline, reconciliation }`. timeline이 reconciliation에 의존하므로 순환은 없다.

### NumberGuard — 이 설계의 요점

모델이 지어낸 숫자는 근거 있는 숫자와 **문장에서 구별되지 않는다.** "차액 3,000원"과 "차액 3,200원"은 읽는 사람에게 똑같이 그럴듯하다. 그래서 사람 검토에 맡길 수 없다 — 검토자도 그 숫자의 출처를 모른다.

프로덕션에서 쓰이는 방식이 이것이다: **출처 시스템에서 찾을 수 없는 값을 참조하면 그 출력을 거부한다.** Uber Genie도 같은 계열로, LLM에 *"제공된 sub-context 안에서만 답하고 출처 URL을 인용하라"* 를 명시적으로 지시한다.

**검사 범위**를 금액(`원` 접미)과 날짜로 한정했다.

| | 넓히면 | 좁히면 |
|---|---|---|
| 맨 숫자까지 검사 | "항목 2개", "3일 이내" 같은 정상 초안이 대량 반려 | — |
| 금액·날짜만 (**채택**) | — | `원` 없는 지어낸 수치가 샐 수 있음 |

초안이 **실제로 주장하는 사실**이 금액과 날짜라서 이 경계로 잡았다. 모델 어댑터가 붙은 뒤 실측해서 조정할 값이다.

### 평가 하네스가 잣대인지도 검증한다

일부러 값을 지어내는 가짜 구현을 함께 돌린다. **전부 통과시키는 하네스는 잣대가 아니다.**

```
[잣대 검증]
  template                 초안 3/4 (75%)  사실정합 3/3 (100%)
  fixture:invents-amount   초안 3/4 (75%)  사실정합 0/3 (0%)
      └ 승인만: [출처에 없는 금액: 270원]
  fixture:invents-date     초안 3/4 (75%)  사실정합 0/3 (0%)
      └ 승인만: [출처에 없는 날짜: 2026-01-01]
```

## 트레이드오프

| | 지금 모델 붙이기 | **포트 + 템플릿 (채택)** | 로컬 Ollama |
|---|---|---|---|
| 규제 | **현행 망분리 예외 대상 아님** | 외부 호출 없음 | 외부 호출 없음 |
| 문장 품질 | 높음 | 낮음(사실 나열) | 중간 |
| 잣대 | 모델에 맞춰 휨 | **먼저 고정** | 먼저 고정 |
| 운영 비용 | 토큰 과금 | 0 | GPU/메모리 |
| 나중 전환 | — | 어댑터 1개 추가 | 어댑터 1개 추가 |

템플릿을 "임시물"로 두지 않은 이유는 두 가지다. **기준선** — 모델이 붙었을 때 "얼마나 나아졌나"를 잴 상대가 필요하다. **폴백** — 모델이 죽거나 검증에 걸렸을 때 상담원이 빈 화면을 보면 안 된다.

Spring AI가 같은 형태를 표준으로 제공한다는 점도 확인했다. `ChatModel`/`ChatClient` 뒤에서 OpenAI·Anthropic·로컬 Ollama가 **의존성과 설정만 바꿔** 교체되고 비즈니스 로직은 그대로다. 우리 `DraftPort`는 그보다 좁은(초안 생성 한 가지) 포트라 어댑터가 Spring AI를 쓰든 직접 호출하든 상관없다.

## 기대치 — 절반쯤 맞는다

| 사례 | 성능 |
|---|---|
| Uber Genie | 도움률 **48.9%** (70,000+ 질문, 13,000 엔지니어링 시간 절감) |
| Meta 인시던트 RCA | 근본원인이 **상위 5개 안에 42%** |
| Zalando 사후분석 | 최신 모델도 **표면적 귀인오류 ~10%** |

"알아서 다 해준다"는 사례는 없었다. **이 전제로 설계했다** — 그래서 초안이지 답변이 아니고, 검증에 걸리면 버린다.

## 하지 않는 것

- **초안을 고객에게 직접 보내지 않는다.** 상담원이 검토·수정 후 발송한다. 토스뱅크 상담 어시스턴트도 같은 형태다 — 실시간 요약과 **응답 초안**을 상담원에게 제공한다
- **초안이 대사 결과를 바꾸지 않는다.** `assist`는 읽기 전용이다. 쓰기를 붙이면 사람 확인 원칙(ADR-008)을 우회하는 뒷문이 된다
- **검증 실패 초안을 "참고용"으로 보여주지 않는다.** 사람은 눈앞의 문장에 끌려가고(앵커링), 틀렸다는 걸 확인할 방법은 없다

## 다음에 열어야 할 것

1. **모델 어댑터** — 망분리 예외가 생성형 AI로 확대되면. 그때 `DraftPort` 구현 하나가 늘고 나머지는 그대로다
2. **블라인드 리뷰** — 상담원이 "초안을 얼마나 고쳤는가"(편집 거리)를 재는 게 먼저다. 처리 시간 단축은 그다음. Klarna의 교훈이 이 순서다
3. **④ 잔여 원인 후보** — ②가 못 가른 것만. `resolveNote` 실데이터가 쌓인 뒤
