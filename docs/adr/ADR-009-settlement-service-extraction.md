# ADR-009. 정산을 별도 서비스로 추출하고, 컨슈머 실패는 재시도 후 DLT로 처리한다

- 상태: 채택 (Accepted)
- 날짜: 2026-08-04
- 관련: [ADR-008](ADR-008-event-contracts-artifact.md)(이벤트 계약),
  [ADR-005](ADR-005-event-externalization-kafka.md)(Kafka 외부화),
  [실측 문서](../performance/msa-baseline-experiments.md)

## 맥락

모놀리스 한계 실측에서 두 문제가 재현됐다(실측 문서 참고).

1. 수평 확장 시 정산 스케줄러가 인스턴스마다 돌아 같은 날짜를 중복 집계하고, 유니크 제약
   위반으로 배치가 실패한다. 애플리케이션 가드(`existsBySettlementDate`)는 동시 진입에 무력했다.
2. 정산·알림처럼 결제와 무관한 모듈의 배포도 전체 재시작을 요구해, 배포당 결제가 9초
   전면 중단됐다(단일 인스턴스 기준).

두 실측이 딜레마를 이룬다. 배포 중단을 롤링으로 풀면 스케줄러 중복이 터지고, 단일 인스턴스로
두면 배포마다 결제가 중단된다. 모놀리스인 한 양쪽을 동시에 만족할 수 없다.

## 결정

정산 모듈을 **별도 Spring Boot 서비스(`settlement-service/`, 독립 Gradle 빌드)**로 추출한다.

- **이벤트 소비**: `payment.confirmed`·`payment.canceled`·`escrow.released`를 Kafka 컨슈머 그룹
  `settlement-service`로 구독한다. 도메인 반영 로직(`SettlementService`)은 무수정 이식이다 —
  인프로세스 시절부터 at-least-once 멱등(절대값 세팅, 상태 가드, 순서 역전 방어)으로 짜여
  있었기 때문이다.
- **DB 분리**: 전용 스키마 `pay_settlement`. 결제 테이블 조인이 원래 없었으므로 이벤트 데이터만으로
  집계한다.
- **스케줄러 단일 소유**: 일 배치는 이 서비스만 돈다. pay-core는 스케줄러 없이 자유롭게 수평 확장한다.
- **인증**: pay-core가 발급한 JWT(HS256)를 같은 시크릿으로 로컬 검증한다(별도 인증서버 없음).
  코어의 jti denylist 검증은 두지 않는다 — Redis 공유는 인프라 결합이라, 어드민 전용 API +
  짧은 만료로 한정하고 필요 시 폐기 이벤트 구독으로 해소한다.
- **데모 콘솔**: 정산 탭은 `http://localhost:8090`을 직접 호출한다(CORS로 콘솔 오리진만 허용).
  K8s Ingress 도입 시 경로 라우팅으로 same-origin이 되어 제거된다.

### 컨슈머 실패 처리: 재시도 후 DLT (A안)

정산 반영이 실패한 레코드는 1초 간격 3회 재시도 후 `<원본토픽>-dlt`로 격리하고 오프셋을
커밋한다(`DefaultErrorHandler` + `DeadLetterPublishingRecoverer`).

검토한 대안은 B안(오프셋 커밋 보류, 무한 재시도)이다. 유실이 0이지만 Kafka 소비 모델에서
오프셋을 진전시키지 않는 한 그 파티션의 모든 후속 레코드가 정지한다(head-of-line blocking).
`orderNo` 라우팅으로 한 파티션에 여러 주문이 섞이므로, 한 건의 poison이 무관한 주문들의
정산을 전부 막는 것은 수용할 수 없다.

A안의 위험(격리된 건이 자동 처리에서 이탈)은 이 시스템에 이미 있는 최종 방어선이 흡수한다.
대사(reconciliation)가 결제 원장과 정산을 대조해 불일치를 검출하므로, DLT 건은 유실이 아니라
**검출 가능한 미처리**가 된다.

## 실측 (추출 당일, 로컬)

**E2E**: 코어 결제 승인 → Kafka → 정산 적재(PENDING_CONFIRMATION) → 구매확정 →
`escrow.released` → CONFIRMED → 어드민 배치 실행 → 정산 생성(10,000원 → 수수료 270 +
VAT 27 → 지급액 9,703, 지급일 +2영업일). 코어 발급 admin 토큰이 정산 서비스에서 검증됐고,
무토큰 401 / USER 토큰 403.

**Poison message**: 깨진 JSON을 `payment.confirmed`에 주입 → 4회 시도(최초 1 + 재시도 3) →
`payment.confirmed-dlt`에 원문 격리 → **직후 정상 결제가 그대로 처리됨**(파티션 비정지).
A안이 의도대로 동작함을 확인했다.

**배포 결합 해소(before/after)**: 결제 부하(30VU) 중 정산 서비스를 재시작했다.

| | 모놀리스(before) | 분리 후(after) |
|---|---|---|
| 결제 실패 | 270건, 9초 전면 중단 | **0건 / 10,200 요청** |
| 이벤트 유실 | 해당 없음 | **0건** — 결제 5,072 = 정산 적재 5,072 |

정산 서비스가 내려가 있는 동안 이벤트는 브로커에 쌓였고, 재기동한 컨슈머가 커밋된 오프셋부터
이어서 전부 처리했다. "정산이 죽어도 결제는 계속되고, 복구되면 하나도 잃지 않는다"가 실측으로
증명됐다.

## 정직한 한계

- **정산 서비스 자체의 다중화는 미해결이다.** 이 서비스를 2개 띄우면 스케줄러 중복이 그대로
  재발한다(컨슈머 그룹은 파티션을 나누지만 `@Scheduled`는 나누지 않는다). 현 단계는 단일
  레플리카 전제이고, 다중화가 필요해지면 ShedLock/리더 선출을 붙인다. 추출이 해결한 것은
  "결제의 스케일링이 정산 스케줄러를 복제하는 결합"이지, 정산 스케줄러의 HA가 아니다.
- **DLT 재처리 운영 루프가 아직 없다.** 격리된 메시지의 조회·재발행 어드민은 후속 과제다
  (notification 모듈의 DLQ 어드민과 같은 패턴).
- **기존 pay DB의 settlement 테이블은 이력으로 남는다**(마이그레이션 불변 원칙). 코어는 더 이상
  접근하지 않으며, 운영 전환이라면 과거 데이터 이관 절차가 필요하다.
