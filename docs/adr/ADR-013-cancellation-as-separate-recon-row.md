# ADR-013. 취소를 대사에 별도 행으로 쌓는다 (덮어쓰지 않는다)

- 상태: 채택 (Accepted)
- 날짜: 2026-08-30
- 관련: [ADR-008](ADR-008-recon-mismatch-analysis-assistant.md), [ADR-012](ADR-012-rule-based-cause-classifier.md), [11 문서 13절](../11-AI-운영자동화-검토.md)

## 맥락 — 재현으로 확인한 결함

대사의 내부 기준 스냅샷(`internal_records`)은 결제 승인 시점에 만들어지고,
취소가 오면 `applySettleableBalance`로 **금액을 덮어쓴다.**

```java
void applySettleableBalance(long settleableBalance) {
    this.amount = settleableBalance;   // trade_date는 그대로, amount만 갈아끼움
}
```

### 실제로 재현했다

로컬에서 승인 → 대사 확정 → 부분취소 순으로 실행한 결과다.

| 단계 | 내부 스냅샷 | 대사 판정 |
|---|---|---|
| ① 10,000원 승인 | 10,000 | — |
| ② 대사 실행 | 10,000 | **MATCHED (확정)** |
| ③ 3,000원 부분취소 | **7,000** | **10,000 (그대로)** |

**확정된 판정과 현재 스냅샷이 갈라진다.**

이건 추정이 아니라 재현 결과다. 같은 거래일 안에서도 갈라지고,
**취소가 며칠 뒤에 오면 더 나쁘다** — 그 날짜를 다시 대사할 이유가 없으니
아무도 모른 채 남는다.

### 왜 이게 문제인가

**① 이미 나간 판정을 사후에 무효로 만든다.**
8/28을 `MATCHED`로 닫아놓고 스냅샷만 바뀐다. 그 날짜를 재실행하면 판정이 뒤집히는데,
재실행할 계기가 없다. **대사의 결론이 조용히 낡는다.**

**② PG 파일의 실제 형태와 어긋난다.**
주요 PG는 환불을 **취소가 일어난 날의 파일에 별도 행**으로 싣는다
(Adyen `Refunded` journal type 등, [11 문서 13절](../11-AI-운영자동화-검토.md)).
8/30 파일에 `-3,000`이 오는데 우리 8/30 스냅샷에는 그 주문이 없다(8/28에 있으므로).
→ **`EXTERNAL_ONLY`로 잡힌다.** 정상 환불이 예외 큐를 오염시킨다.

**③ 이 프로젝트가 이미 지키는 원칙과 반대다.**
원장은 정정을 **역분개로만** 한다. 행을 고치지 않는다.
그런데 대사 스냅샷은 덮어쓰고 있다. 같은 이유(사후 재구성 가능성)가 여기도 적용된다.

> 토스페이먼츠도 같은 방향으로 갔다 — *"집계 방식 저장이라 오류 원인 추적이 불가했던 문제를
> 거래 단위 1:1 저장으로 전환"*.

## 결정

**취소를 원 거래일의 금액 수정이 아니라, 취소가 일어난 거래일의 별도 행으로 쌓는다.**

```
8/28  ord-1  +10,000   (승인)
8/30  ord-1   -3,000   (취소)   ← 새 행. 8/28은 건드리지 않는다
```

- 과거 판정이 **불변**이 된다
- PG 파일 구조와 **모양이 같아진다** — 양쪽 다 "취소일에 음수 행"
- 원장의 역분개 원칙과 **같은 형태**다

## 트레이드오프

### 유니크 제약을 바꿔야 한다

지금은 **`order_no` 단독 유니크**라 한 주문에 한 행뿐이다(날짜별도 아니다 — 실제 스키마를 확인하고 정정했다).
취소를 별도 행으로 쌓으려면 이 제약이 걸린다.

- **제약을 푼다** → 중복 적재를 막던 장치가 사라진다. ❌
- **키에 구분자를 더한다** → `(order_no, seq)`.
  승인은 `seq=0`, 취소는 취소 순번을 쓴다. ✅ 채택.
  이미 `PaymentCanceledEvent`에 `cancelSeq`가 있어 그대로 쓸 수 있다.

### 취소 이벤트에 시각이 없다

`PaymentCanceledEvent(orderNo, paymentId, cancelSeq, cancelAmount, settleableBalance, fullyCanceled)` —
**언제 취소됐는지가 없다.** 그래서 "어느 거래일에 쌓을지"를 정할 수 없다.

- **수신 시각(`Instant.now()`)을 쓴다** → ❌. 아웃박스 소비가 밀리면 거래일이 바뀐다.
  컬리가 겪은 것과 같은 함정이다(발행 시각으로 윈도우를 할당해 23:59 건이 다음 날로 감).
- **이벤트에 `canceledAt`을 추가한다** → ✅ 채택. 사실이 일어난 시각을 페이로드에 싣는다.
  승인 경로가 이미 `approvedAt`을 싣고 있어 **일관된다.**

### 대사 조회가 합산이 된다

내부 기준이 한 행이 아니라 여러 행이 되므로, 조회 시 **주문별 합산**이 필요하다.
외부 기록은 이미 합산하고 있어(11 문서 13절) 양쪽이 같은 모양이 된다.


## 고친 뒤 재현 결과

같은 시나리오를 다시 돌렸다.

| | 고치기 전 | 고친 후 |
|---|---|---|
| 승인 행 | 10,000 → **7,000으로 덮어씀** | **10,000 그대로** (`seq=0`) |
| 취소 | 기록 없음 | **-3,000 별도 행** (`seq=1`) |
| 확정된 판정 | 10,000 — **스냅샷과 갈라짐** | 10,000 — **일치 유지** |

```
순번  금액      거래일
0     10000    2026-08-30
1     -3000    2026-08-30
```

테스트 4건으로 고정했다 — 음수 행으로 쌓임 / 취소일 기준 거래일 / 멱등 / 승인 스냅샷 없을 때 무시.
그리고 같은 거래일에 승인·취소가 다 있으면 합산되는 것도 확인했다.

## 작업 중 배운 것

**이름이 같다고 같은 문제가 아니다.** 정산 모듈에도 `applySettleableBalance`가 있는데
그건 지급액을 잔액으로 세팅하는 것이라 **덮어쓰는 게 맞다.** 대사 쪽만 고쳤다.
전역 검색으로 같은 이름을 찾아 일괄 수정했다면 정산을 망가뜨렸을 것이다.

## 하지 않는 것

- **과거 판정을 소급 수정** — 이미 나간 결론은 그대로 둔다.
  바꿔야 한다면 그 날짜를 다시 대사하는 것이 명시적이다.
- **`applySettleableBalance` 유지** — 덮어쓰기가 결함의 원인이므로 제거한다.
