# 결제 트랜잭션 안의 포인트 적립 경합을 개선하는 방법

성능 이야기이기도 하고 정합성 이야기이기도 하다. 조회수 카운터라면 성능만 보면 되지만,
포인트는 돈이라 **근사치도 유실도 허용되지 않는다.** 이 제약이 해결책 선택을 바꾼다.

발단은 부하 실험이었다. 체크아웃 부하 스크립트를 처음 돌렸을 때 결제 승인이 대량으로 500을
반환했고, 로그의 범인은 결제가 아니라 **포인트 적립**이었다.

```
ObjectOptimisticLockingFailureException:
  Row was updated or deleted by another transaction ... [PointAccount#1]
```

## 분석

적립 구조는 단순하다. 결제 완료 시 실결제액의 1%를 적립하는데, 적립이 결제 트랜잭션 안에서
`계좌 로드 → balance += n → 저장`으로 실행되고, 계좌에는 `@Version` 낙관적 락이 걸려 있다.

경합 특성을 따져 본다.

- 적립 경합은 **같은 사용자의 동시 결제**에서만 발생한다. 서로 다른 사용자는 서로 다른 행이다.
- 그런데 운영 구성에는 사용자별 rate limit(5/s)이 있다. 같은 사용자의 폭주를 유입 층에서
  차단하므로 **이 경합은 운영에서 거의 노출되지 않는다.** limiter가 동시성 결함의 완충
  역할을 해온 것이다.
- 노출 빈도가 낮다고 결함이 아니게 되는 건 아니다. limiter 설정 변경, 내부 배치의 일괄 적립,
  또는 향후 적립 경로 추가가 언제든 이 지뢰를 밟는다. 그리고 실패의 반경이 나쁘다. 적립
  충돌이 **결제 승인 자체를 500으로** 만든다. 부가 기능이 본 기능을 죽이는 구조다.
- 조회수 문제와 결정적으로 다른 제약: 포인트 잔액은 원장 이력과 1원 단위로 일치해야 한다.
  근사 집계·유실 허용 해법은 시작부터 배제된다.

측정부터 했다. limiter를 끄고(경합을 가리는 변수 제거) 계정 하나로 30VU가 주문→승인을
반복하는 최악 조건을 만들었다 (`k6/point-contention.js`).

**BEFORE: 승인 성공률 39.6%** (7,625건 중 4,603건 실패, 전부 낙관적 락 충돌).

## 해결책

### 1. 현행 유지 + 낙관적 락 재시도

- 충돌 시 몇 번 다시 읽어 다시 쓰면 대부분 성공한다. 코드 몇 줄이면 된다.
- 그러나 경합 자체는 그대로라 부하가 오르면 재시도도 소진된다. 재시도 동안 결제 트랜잭션이
  길어지는 것도 나쁘다. 커넥션 점유가 늘고, 실패 반경(적립→결제)이 여전하다.
- 증상 완화지 치료가 아니라서 기각.

### 2. DB 원자 증가 (upsert)

- 적립은 더하기다. 더하기는 순서가 무관하다(교환법칙). 순서가 무관한 연산을 굳이 읽어서
  순서를 만들 이유가 없다. `UPDATE ... SET balance = balance + n`으로 DB에 맡기면
  낙관적 락 충돌이라는 개념 자체가 사라진다.
- 재고 차감에서 락 3종을 실측 비교해 조건부 UPDATE를 채택했던 것(ADR-004)과 같은 처방이다.
  차이는 재고엔 조건(`quantity >= n`)이 필요했고 적립엔 필요 없다는 것뿐.
- 계좌가 아직 없는 첫 적립의 생성 레이스는 `INSERT ... ON DUPLICATE KEY UPDATE` 한 문장으로
  흡수한다.
- **함정 하나**: 네이티브 증가는 `@Version`을 우회한다. version을 안 올리면, 동시에 엔티티로
  로드된 다른 경로(포인트 사용·환불)가 낡은 balance로 덮어써도 버전 검사를 통과해 **적립분이
  소리 없이 사라진다**(lost update). 그래서 `version = version + 1`을 함께 올려, 그 경로들이
  기존처럼 충돌을 감지하게 유지한다.

### 3. 적립을 결제 트랜잭션에서 분리 (이벤트 비동기)

- 근본 구조 개선이다. 적립 실패가 결제를 못 죽이게 되고, 결제 트랜잭션도 짧아진다.
  적립은 이미 orderNo 멱등이라 재전달에도 안전하다.
- 대신 계약이 바뀐다. 적립이 몇 초 늦게 보일 수 있고, "승인 응답 = 적립 완료"를 전제한
  코드·테스트가 모두 움직여야 한다. 취소(회수)와의 순서 관계도 다시 따져야 한다.
- 2안이 경합을 이미 제거하므로, 3안의 남은 가치는 "실패 격리"다. 그 가치는 인정하되
  이번 범위에서는 계약 변경 없이 문제를 잡는 쪽을 택하고, 3안은 후속 과제로 기록한다.

### 4. Redis 카운팅 후 주기 flush

- 조회수라면 정답 후보다. 포인트에서는 기각한다. flush 전 크래시가 곧 **돈의 유실**이고,
  잔액과 이력의 일치를 실시간으로 보장할 수 없다. 같은 +1 문제라도 정확도 요구가 다르면
  답이 달라진다.

## 선택과 실측

**2안(원자 증가)을 채택**했다. 동작 계약을 바꾸지 않으면서 경합의 뿌리를 제거하고, 구현이
한 문장이다. 같은 조건으로 재실험했다.

| | BEFORE (낙관적 락) | AFTER (원자 증가) |
|---|---|---|
| 승인 성공률 | **39.6%** (3,022/7,625) | **100.00%** (6,761/6,761) |
| 실패 원인 | 전부 @Version 충돌 | 없음 |
| 승인 p95 | — | 134ms (동일 부하) |

정합 검증으로 원자 증가가 유실 없이 전부 반영됐는지 원장과 대조했다.

```
balance = 978,400  /  Σ(EARN) − Σ(EARN_REVERSAL) = 978,400  /  EARN 9,784건
→ 불일치 0
```

## 남긴 것

- **3안(이벤트 비동기 적립)은 후속 과제다.** 경합은 잡혔지만 "적립 실패가 결제를 실패시킬 수
  있는 구조"는 남아 있다(현재 남은 실패 경로는 DB 자체 장애 정도). 실패 격리가 필요해지는
  시점에 진행한다.
- rate limiter가 가려주는 동시성 결함이 더 있을 수 있다. 부하 실험은 limiter를 끄고도
  돌려봐야 한다는 것이 이 사건의 교훈이다.
